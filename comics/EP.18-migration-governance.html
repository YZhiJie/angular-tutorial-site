EP.18 迁移不重写 ​

对应正文：18-migration-governance（1 迁移误区 / 2 六阶段路线 / 4 边界规则 / 6 版本治理 / 7 常见坑）· 配套示例：routing-form

剧情回顾 ​

  • 第 1 格：像素酱接到「三个月迁移完、停需求全部重写」的要求。一次性重写把风险集中到发布日，还留下了 signal 与 BehaviorSubject 两套状态。
  • 第 2 格：码叔给出六阶段路线——盘点依赖、升级工具链、结构迁移、收紧 DI 边界、领域逻辑下沉、最后清理过渡代码。
  • 第 3 格：标签君演示边界规则：UI → Facade → Domain 单向依赖，ESLint 阻止反向 import，公共 API 只从 index.ts 导出。
  • 第 4 格：码叔结案——先边界、后替换；能回滚的小步，才敢连续发布。

知识点拆解 ​

第 1 格 · 一次性重写的代价 ​

「停需求三个月再上线」意味着：需求积压、风险集中在发布日、回滚成本极高。迁移真正难的不是换语法，而是边界与顺序。

双真源是常见后遗症：

ts
count = signal(0);
count$ = new BehaviorSubject(0);

两套状态同时存在，谁先更新、谁是真值都说不清。

第 2 格 · 六阶段路线 ​

阶段内容风险可批量
①盘点依赖与阻塞点低否
②升级工具链与主版本中是
③结构与样式迁移低是
④状态与 DI 边界收紧中否
⑤领域逻辑下沉高否
⑥清理过渡代码与双真源低是

机械步骤先做，涉及语义的步骤后做；每一步都要能独立发布与回滚。

第 3 格 · 边界规则 ​

依赖方向只能单向：

txt
UI / 组件  →  Facade（用例编排）
Facade     →  Domain（实体、规则、纯函数）
Domain     ↛  UI

用 ESLint boundaries 或 import/no-restricted-paths 把规则固化，而不是靠代码评审自觉。公共 API 从 index.ts 导出，内部文件禁止被跨模块直接引用。

第 4 格 · 版本治理 ​

  • Angular 主版本、Node 版本、构建器版本写进 package.json 与锁文件；
  • 升级前先跑兼容性 lint 与全量测试，再合并；
  • 过渡期允许适配层，但必须登记负责人与删除时间；
  • 每完成一个阶段，删除对应的过渡代码，避免「临时方案」永久化。

坑点清单 ​

🔗 正文对照：常见坑表格

  1. 一次性重写 → 风险集中到发布日，改为可回滚的小步；
  2. 保留双真源 → signal 与 Subject 长期并存，清理阶段必须删除一套；
  3. 版本不写进锁文件 → 环境间行为漂移，升级不可复现；
  4. 只在评审里口头约定边界 → 换个 reviewer 就失守，改用 lint 固化；
  5. 过渡代码没有负责人与期限 → 临时方案永久化。

自测 3 题（含答案） ​

  1. 为什么「停需求重写」通常不是好方案？——它把风险集中到单次发布，期间需求积压、回滚困难；分阶段小步迁移可以每步发布、每步回滚，问题定位也更早。
  2. 双真源为什么必须清理？——两套状态同时存在会产生更新顺序与真值归属不清，长期造成数据不一致与重复渲染；迁移结束时只能保留一套。
  3. 边界规则为什么要用 lint 而不是评审？——评审依赖人的记忆与状态，人员变化就会失守；lint 把规则变成可执行、可重复的门禁。
