EP.11 大型应用怎么分层 ​

对应正文：11-architecture（1 组件直接取数的代价 / 2 机制拆解 / 3 可运行示例 / 4 代码拆解 / 5 常见坑）· 配套示例：architecture

剧情回顾 ​

  • 第 1 格：标签君发现组件里直接注入 HttpClient 的代价——30 个模块互相 import 形成循环。展示、校验、请求、状态全压组件，想换缓存改组件、想加提示改组件、想脱离网络测试还得改组件。
  • 第 2 格：码叔展示四层分工——core 只声明接口、InjectionToken 提供运行时键、Facade 收敛状态与用例、app.config.ts 是唯一装配点。依赖方向只允许从外向内（feature → core）。
  • 第 3 格：像素酱做实证——架构分层图清晰地展示依赖箭头只向 core 指；测试里用 Fake 实现通过 Token 替换，Facade 代码零改动；Facade 用 private state = signal() + readonly orders = state.asReadonly() 收敛状态。
  • 第 4 格：码叔结案——分层不是拆文件多，而是让变化被隔离在一层里。四个关键原则：依赖倒置、Token 绑定、Facade 收敛、组合根唯一。

知识点拆解 ​

第 1 格 · 反例的代价 ​

ts
// 反例：展示、校验、请求与状态都压在一个组件里
export class OrdersPage {
  private readonly http = inject(HttpClient);
  protected readonly orders = signal<Order[]>([]);

  load(): void {
    this.http.get<Order[]>('/api/orders')
      .subscribe((orders) => this.orders.set(orders));
  }
}

三个方向同时变脆：换数据源改组件、加错误提示改组件、脱离网络测试改组件。第二个页面要订单列表时只能复制一遍逻辑。

第 2 格 · 四层分工 ​

领域模型与仓储接口（core）：只描述「需要什么能力」，不描述「怎么取」。core 只依赖 RxJS 的 Observable 与自身模型，不知道 HTTP、缓存或存储的存在。

ts
// core/order.repository.ts
export interface OrderRepository {
  list(): Observable<Order[]>;
  create(title: string, amount: number): Observable<Order>;
}

InjectionToken：接口在编译后被擦除，Token 提供运行时注入键。

ts
// core/tokens.ts
export const ORDER_REPOSITORY = new InjectionToken<OrderRepository>('OrderRepository');

Facade：收敛状态与用例，私有可写 signal 加公开只读视图。组件只做两件事——把用户输入转成 Facade 调用、把 Facade 的 signal 映射到模板。

ts
// features/orders/orders.facade.ts
private readonly repository = inject(ORDER_REPOSITORY);
private readonly state = signal<Order[]>([]);
readonly orders = this.state.asReadonly();
readonly total = computed(() =>
  this.state().reduce((sum, o) => sum + o.amount, 0),
);
readonly loading = signal(false);
readonly error = signal('');

第 3 格 · 组合根是唯一装配点 ​

app.config.ts 是唯一知道「接口由哪个实现提供」的地方：

ts
export const appConfig: ApplicationConfig = {
  providers: [
    provideBrowserGlobalErrorListeners(),
    { provide: ORDER_REPOSITORY, useClass: InMemoryOrderRepository },
  ],
};

InMemoryOrderRepository 不标 providedIn: 'root'，因为它必须通过 Token 注册。测试时用 TestBed 把 Token 覆盖为同步 Fake，即可断言 orders()、total() 与 error() 而不访问网络。

第 4 格 · Facade 的 load / add ​

ts
load(): void {
  this.loading.set(true);
  this.error.set('');
  this.repository.list().subscribe({
    next: (orders) => {
      this.state.set(orders);
      this.loading.set(false);
    },
    error: () => {
      this.error.set('订单加载失败，请稍后重试');
      this.loading.set(false);
    },
  });
}

add(title: string, amount: number): void {
  if (!title.trim() || amount <= 0) {
    this.error.set('请填写有效的订单名称与金额');
    return;
  }
  this.error.set('');
  this.repository.create(title.trim(), amount).subscribe((order) => {
    this.state.update((orders) => [...orders, order]);
  });
}

加载开始先清错误，失败同时收尾 loading；新增先做校验，再用 update 返回新数组保证 signal 通知生效。Facade 不暴露 repository，组件无法绕过校验直接写数据。

坑点清单 ​

🔗 正文对照：常见坑表格

  1. 组件绕过 Token 直接注入具体类 → 耦合展示与实现，只注入 Facade，由组合根决定实现；
  2. Facade 暴露可写 signal → 组件能绕过校验直接 set，私有 state 只公开 asReadonly() 或派生值；
  3. 启动时报 NullInjectorError → Token 未在 app.config.ts 注册；
  4. InMemoryOrderRepository 加了 providedIn: 'root' → 产生无人使用的类级单例，容易让调用方误以为可以直接注入具体类，破坏依赖倒置。

自测 3 题（含答案） ​

  1. 为什么仓储要用 InjectionToken，而不是直接注入类？——接口在运行时不存在，Token 提供稳定注入键；同时把「需要什么能力」与「由谁实现」分开，组件只依赖 Token，替换实现时只改组合根。
  2. Facade 与普通服务有什么区别？——普通服务可以只封装一个能力；Facade 面向一个用例边界，负责组合仓储、维护加载与错误状态、暴露只读派生值。判断标准：组件是否只需要与一个对象交互就能完成整个页面。
  3. 为什么 InMemoryOrderRepository 不加 providedIn: 'root'？——因为它必须由 Token 绑定，而不是按类本身注入。若加了会额外产生一个无人使用的类级单例，也容易让调用方误以为可以直接注入具体类，破坏依赖倒置。
