EP.03 DI 那张透明网 ​

对应正文：03-di-service（1 依赖注入解决的三个问题 / 2 动手步骤 / 3 可运行示例 / 4 代码拆解 / 5 常见坑 / 7 自测）· 示例：examples/di-service · Playground id：di-service

剧情回顾 ​

  • 第 1 格：标签君发现两个 CounterPanel 各自 +10 互不影响——检查代码：一个组件里写了 providers: [CounterStore]，另一个用 providedIn: 'root'。注册位置决定作用域。
  • 第 2 格：码叔画出 DI 查找链三步走：host 自己的 providers → 逐个父级 → root 注入器。inject() 必须在注入上下文（字段初始化、构造函数、工厂函数）里调。
  • 第 3 格：像素酱演示 InjectionToken + optional 的组合拳——配置对象、常量这类非类依赖也能优雅注入，缺省时回退默认值而不是抛 NullInjectorError。
  • 第 4 格：码叔结案——服务内私有 signal + asReadonly() 暴露只读视图，写入方法收敛在服务内部，外部只能调用 increase / reset，不能绕过日志逻辑。

知识点拆解 ​

第 1 格 · 同一个 Service 怎么会有多份实例？ ​

注册位置 = 作用域边界：

写法创建时机共享范围摇树
@Injectable({ providedIn: 'root' })根注入器首次需要时全局单例✅ 没用时会被移掉
组件 providers: [Store]组件实例化时该组件及其子组件❌
appConfig.providers应用启动时全局单例✅

共享状态放根级，局部状态放组件级。两个并列面板要同步，Store 必须是 root 单例——任何一个组件的 providers: [Store] 都会制造独立实例，状态就不再同步。

第 2 格 · DI 查找链三步 ​

当你在某个组件里 inject(CounterStore) 时，Angular 按顺序找：

① 组件自己的 providers → 找到就用，停
② 父组件的 providers   → 没找到向上走
③ ...一直走到根注入器   → 找到返回，找不到抛 NullInjectorError

@Optional() 让找不到时返回 null 而不是报错——配合空值合并 ?? 给默认值。

inject() 的注入上下文：字段初始化器、构造函数参数、工厂函数都可以调；放到 setTimeout、按钮回调、普通方法里会抛 InjectorLifecycleError——因为那时 Angular 已经离开了当前注入器的作用域。

第 3 格 · InjectionToken 给非类依赖发身份证 ​

Angular 的 DI 令牌默认靠类的身份识别。配置对象、字符串常量没有类怎么办？用 InjectionToken<T>：

ts
// 1. 定义令牌（带泛型，类型安全）
export const LOGGER_PREFIX = new InjectionToken<string>('日志前缀');

// 2. 应用级注册
// app.config.ts
providers: [
  { provide: LOGGER_PREFIX, useValue: '[演示]' },
]

// 3. 消费时 optional + 兜底
// logger.ts
private readonly prefix =
  inject(LOGGER_PREFIX, { optional: true }) ?? '[app]';
  • useValue 直接提供一个值；
  • useFactory 提供一个工厂函数（适合复杂初始化）；
  • 字符串令牌没有类型信息，也容易碰撞——一律用 InjectionToken。

第 4 格 · 服务里用 signal 封装状态 ​

服务是跨组件共享的状态容器，signal 封装是最佳实践：

ts
@Injectable({ providedIn: 'root' })
export class CounterStore {
  private readonly state = signal(0);          // 私有：外部无法直接写
  readonly count = this.state.asReadonly();     // 只读视图
  readonly double = computed(() => this.count() * 2);

  increase(step = 1): void {
    this.state.update((v) => v + step);         // 唯一入口，可加日志
    this.logger.log('count -> ' + this.state());
  }
}
  • asReadonly() 返回没有 set / update 的只读 signal，类型层面阻止越权；
  • computed 把派生逻辑（比如 double = count * 2）集中到服务内，自动随依赖重算；
  • 数组更新用 .update(list => [...list, 新项]) 生成新引用，signal 只有在引用变化时才通知消费者——直接 push 原数组没用。

坑点清单 ​

🔗 正文对照：常见坑表格

  1. 两个面板状态不同步 → 各自 new CounterStore() 或组件重复声明 providers，用 providedIn: 'root' 或在共同父级提供；
  2. 报 NullInjectorError（找不到令牌） → InjectionToken 没注册且没加 optional，补 useValue 注册或 { optional: true } + 默认值；
  3. 日志数组更新后界面不变 → 直接 push 原数组，引用未变，用 .update(list => [...list, 新项])；
  4. 外部代码能直接改服务状态 → 暴露了可写 signal，用 asReadonly() 收敛写入口；
  5. inject() 放错位置 → 必须在注入上下文调用，字段初始化器最简洁。

自测 3 题（含答案） ​

  1. providedIn: 'root' 与组件 providers 有什么本质区别？——前者由根注入器创建并缓存，整个应用共享一个实例，且可被摇树优化；后者由组件注入器创建，每个组件实例各有一份，作用域限定在该组件及其子组件。共享状态应放根级。
  2. 为什么配置项要用 InjectionToken，而不是字符串令牌？——字符串令牌没有类型信息，容易与其他库的令牌重名；InjectionToken<T> 带泛型，注入结果有静态类型检查，并且对象身份唯一不会碰撞。
  3. 服务里的 signal 为什么要 asReadonly()？——直接暴露可写 signal，任何消费者都能绕过服务内的日志与校验直接 set / update。asReadonly 只保留读取能力，把写入口收敛到服务方法，便于维护不变量。
