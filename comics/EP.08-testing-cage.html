EP.08 把代码关进测试笼子 ​

对应正文：08-testing（1 先让逻辑可测 / 2 测试分层与 Vitest 行为 / 3 可运行示例 / 4 代码拆解）· 配套示例：testing-lab · Playground id：testing-lab

剧情回顾 ​

  • 第 1 格：标签君在测试里改了 signal 但 nativeElement 还是旧值——zoneless 下 signal 变了不会自动刷新模板！必须显式 fixture.detectChanges()。
  • 第 2 格：码叔拆解两个测试维度——纯函数测试（打底，毫秒级稳定）和 TestBed 组件测试（只在需要验证 DI、模板、DOM 事件时用）。先把逻辑提取成纯函数，再谈怎么测组件。
  • 第 3 格：像素酱画出 syncTestBed + fakeAsync + tick 三件套，以及 HttpClientTestingModule 的用法——可控的假响应、验证请求参数、连取消请求都能捕获。
  • 第 4 格：码叔结案——测试金字塔：底座大量纯函数测试覆盖业务规则和边界条件，塔顶少量组件测试覆盖关键交互。三个坑点：只测正常路径、浮点断言、忘记 detectChanges。

知识点拆解 ​

第 1 格 · detectChanges 那个坑 ​

zoneless 下 signal.set() 写入不会自动让 ComponentFixture 刷新模板——这和 Zone.js 时代完全不同：

ts
it('更新 signal 后刷新视图', fakeAsync(() => {
  const fixture = TestBed.createComponent(App);
  fixture.detectChanges();  // ✅ 首次触发变更检测，模板刷新

  fixture.componentRef.items.set(newItems);  // signal 写入
  tick();                    // ✅ 跑所有待执行的 async task
  fixture.detectChanges();   // ✅ 再触发一次变更检测

  expect(fixture.nativeElement.textContent).toContain('1655');
}));

signal 变化检测是异步的——调度器把刷新任务排到微队列里，所以组件测试里通常需要 fakeAsync + tick + detectChanges 三件套。

第 2 格 · 先让逻辑可测 ​

把业务规则提取成纯函数——无 DI、无 DOM、无 signal、输入确定输出确定：

ts
// src/app/price.ts —— 纯函数，独立于组件
export function subtotal(items: CartItem[]): number {
  return items.reduce((sum, item) => 
    sum + item.price * item.quantity, 0);
}

export function applyDiscount(amount: number, rate: number): number {
  if (rate < 0 || rate > 1) throw new RangeError('...');
  return Math.round(amount * (1 - rate) * 100) / 100;
}

组件只负责把纯函数接到 signal 上：

ts
// src/app/app.ts —— 薄组件
protected readonly items = signal<CartItem[]>([...]);
protected readonly subtotal = computed(() => subtotal(this.items()));
protected readonly discounted = computed(() => 
  applyDiscount(this.subtotal(), 0.1));

为什么要这样做？ 测试一个加法，不需要启动 Angular 运行时、不需要渲染 DOM、不需要处理 Zone.js——直接 expect(subtotal(items)).toBe(997) 就行，毫秒级稳定。

第 3 格 · TestBed 何时出场 ​

TestBed 只在你需要验证以下内容时才值得用：

需求TestBed 提供什么
DI 注入是否正确伪造完整的 DI 树
模板绑定是否生效创建真实组件 + 渲染模板
DOM 事件模拟 click、input 等
路由/表单交互RouterTestingModule / ReactiveFormsModule
HTTP 请求HttpClientTestingModule
ts
// HttpClientTestingModule 用法
TestBed.configureTestingModule({
  imports: [HttpClientTestingModule],
  providers: [UserService]
});

const http = TestBed.inject(HttpTestingController);
const userService = TestBed.inject(UserService);

userService.search('angular').subscribe(users => {
  expect(users.length).toBe(3);
});

const req = http.expectOne('/api/users?term=angular');
expect(req.request.method).toBe('GET');
req.flush(mockUsers);  // 可控的假响应

第 4 格 · 测试金字塔 ​

       ┌── 少量 TestBed 组件测试 ──┐
       │   · signal → 模板链路      │
       │   · DI 注入正确性          │
       │   · 关键 DOM 事件          │
       └───────────────────────────┘
    ┌────────── 大量纯函数测试 ──────────┐
    │  · 业务规则（累加、折扣、舍入）      │
    │  · 边界条件（空数组、0、1、负数）   │
    │  · 异常分支（非法折扣率抛 RangeError）│
    └───────────────────────────────────┘

ng test 实际跑的是什么？

bash
ng test --watch=false
# 等价于 @angular/build:unit-test 构建器
# → 编译 TS + 模板类型检查
# → 收集 src/**/*.spec.ts
# → Vitest 在 jsdom 环境运行
# → CI 中失败以非零状态退出

质量门禁三连：ng test --watch=false 确认逻辑 → npm run build 确认构建与预算 → 合并主分支。

坑点清单 ​

🔗 正文对照：常见坑表格

  1. 一个加法也要创建组件才能测 → 逻辑写在组件方法里，提取纯函数让组件只做组合；
  2. 测试全绿但线上出错 → 只覆盖正常路径，补空数组、0、1、非法参数等边界；
  3. 浮点断言偶发失败 → 二进制浮点无法精确表示小数，金额先舍入到两位，或用 toBeCloseTo；
  4. 纯函数测试也套 TestBed → 没有 DI、模板或 DOM 需求，直接调用函数减启动成本；
  5. CI 中 ng test 一直不退出 → 监听模式没关，用 --watch=false；
  6. 新增 spec 没被执行 → 文件名不符合 *.spec.ts，确认 tsconfig.spec.json 的 include；
  7. 组件测试读文本拿不到值 → 创建后没触发首次变更检测，调用 fixture.detectChanges()。

自测 3 题（含答案） ​

  1. 为什么示例把计价逻辑放在纯函数里，而不是组件方法里？ —— 纯函数没有 DI、DOM 与生命周期依赖，测试只需构造输入、断言输出，运行快且稳定。组件方法要经过 TestBed、模板渲染与变更检测才能验证同一个加法，成本高且失败原因不直观。

  2. 什么情况下应该使用 TestBed？ —— 需要验证依赖注入、模板绑定、DOM 事件、路由或表单交互时。若测试对象只是一个不依赖 Angular 运行时的计算函数，TestBed 不提供额外价值，只会拖慢测试。

  3. ng test 在示例项目里实际做了什么？ —— 它调用 @angular/build:unit-test 构建器，编译 TypeScript 与模板，收集 src/**/*.spec.ts，再交给 Vitest 在 jsdom 环境运行。CI 中用 --watch=false 只跑一次，失败时以非零退出码结束。
