EP.04 路由门卫与响应式表单 ​

对应正文：04-routing-form（1 路由、参数与表单的三条主线 / 2 动手步骤 / 3 可运行示例 / 4 代码拆解 / 5 常见坑 / 7 自测）· 示例：examples/routing-form · Playground id：routing-form

剧情回顾 ​

  • 第 1 格：标签君写 canActivate 返回 Observable<boolean>，页面还是闪了一下——其实 Router 会自动订阅并等待，第一个 emit 值才是放行/拦截的判断；白屏是组件首屏渲染，不是守卫没起作用。
  • 第 2 格：码叔画出守卫执行顺序 canActivate（父→子）→ resolve 预加载 → 渲染。三种返回值 Router 都能处理：boolean 立即判断、Promise<boolean> 等 resolve、Observable<boolean> 等首个 emit。永远不 resolve → 路由挂起。
  • 第 3 格：像素酱展示响应式表单的 FormBuilder.nonNullable.group——nonNullable 让值类型收敛为 string 而不是 string | null；跨字段校验器挂在 group 上，因为它需要同时读多个控件。
  • 第 4 格：码叔结案——错误展示靠 touched + hasError，提交时调 form.markAllAsTouched() 让所有错误同时可见；通配路由 ** 必须放在数组最后。

知识点拆解 ​

第 1 格 · 路由守卫的异步魔法 ​

守卫可以返回三种值，Router 会自动消费并等待：

ts
// 同步守卫：立即返回
canActivate = () => this.auth.isAuthenticated();

// Promise 守卫：等 resolve
canActivate = async () => await checkPermission();

// Observable 守卫：等首个 emit
canActivate = () => this.authService.isLoggedIn$;

Router 的处理逻辑：

  • 返回 false → 拦截，不进入目标路由；
  • 返回 true → 放行；
  • 永远不 resolve / 不 emit → 路由挂起，目标组件永远不渲染；
  • 守卫顺序从父路由到子路由串行执行，一个 false 就截断。

第 2 格 · 三种守卫各管一段 ​

守卫触发时机作用
canActivate将要进入目标路由权限校验、登录态检查
canDeactivate将要离开当前路由未保存表单提醒
resolve进入目标路由之前预加载数据，组件可以直接用
ts
// resolve：预加载数据，组件无需再订阅
{
  path: 'user/:id',
  component: UserDetail,
  resolve: { user: userResolver },
}
// 组件里通过 route.snapshot.data.user 直接拿到

第 3 格 · 响应式表单 vs 模板驱动表单 ​

维度ReactiveFormsModuleFormsModule
模型位置TypeScript 代码里建 FormGroup模板里用 [(ngModel)]
校验函数式 Validator指令属性
跨字段校验✅ 方便❌ 很麻烦
测试直接操作 FormGroup 对象需要 TestBed 模拟输入
类型安全✅ nonNullable.group 有类型❌

推荐用法（带类型的 FormBuilder）：

ts
// nonNullable 让每个控件值类型为 string（不含 null）
this.form = this.fb.nonNullable.group(
  {
    email: ['', [Validators.required, Validators.email]],
    password: ['', [Validators.required, Validators.minLength(8)]],
    confirm: ['', Validators.required],
  },
  { validators: passwordMatch() },  // 跨字段校验器挂在 group 上
);

跨字段校验器返回 null 表示通过，返回对象表示失败：

ts
export function passwordMatch(): ValidatorFn {
  return (group: AbstractControl): ValidationErrors | null => {
    const pwd = group.get('password')?.value;
    const cf  = group.get('confirm')?.value;
    if (!pwd || !cf) return null;          // 空表单交给 required
    return pwd === cf ? null : { passwordMismatch: true };
  };
}

第 4 格 · 错误展示三要素 ​

模板里只在用户触达过字段后才显示错误，避免满屏红字：

html
@if (form.controls.email.touched && form.controls.email.invalid) {
  <p class="error" role="alert">
    @if (form.controls.email.hasError('required')) { 邮箱不能为空。 }
    @if (form.controls.email.hasError('email')) { 合法邮箱。 }
  </p>
}

提交时的正确姿势——一次性标记所有字段 touched，让所有问题同时可见：

ts
protected submit(): void {
  this.submitted.set(true);
  if (this.form.invalid) {
    this.form.markAllAsTouched();     // ← 关键！
    return;
  }
  console.log(this.form.getRawValue()); // 拿全部值（含禁用字段）
}

坑点清单 ​

🔗 正文对照：常见坑表格

  1. 点击导航整页刷新 → 用原生 href 而非 routerLink，改成 routerLink 并导入 RouterLink；
  2. 通配路由抢占了其他页面 → path: '**' 写在具体路由之前，必须放到数组末尾；
  3. 详情页拿不到参数 → 未启用 withComponentInputBinding() 或 input 名称与参数不一致，启用绑定并保持同名；
  4. 提交后没有任何错误提示 → 只检查了 invalid，没标记 touched，提交时调 markAllAsTouched()；
  5. 密码不一致却不报错 → 校验器挂在字段上而不是 group 上，passwordMatch() 放进 group 的 validators。

自测 3 题（含答案） ​

  1. withComponentInputBinding() 解决了什么问题？——它把路由参数、query 参数等按名称绑定到组件的 signal 输入，组件无需注入 ActivatedRoute 再订阅参数流。参数变化时输入自动更新，也省去了手动取消订阅的负担。
  2. 为什么跨字段校验器要挂在 group 上？——passwordMatch 需要同时读取密码与确认密码，字段级校验器只能看到当前控件的值。挂到 group 上后，校验器能通过 group.get() 读取多个控件，并把 passwordMismatch 记录在表单层级，供模板用 form.hasError 查询。
  3. nonNullable 的作用是什么？——默认情况下，控件的值类型包含 null，读取时要做空值判断。nonNullable.group 让控件值类型收敛为 string，模板与提交逻辑都更直接。代价是需要为每个控件提供合理的初始值。
