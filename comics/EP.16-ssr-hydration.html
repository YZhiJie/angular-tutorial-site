EP.16 服务端先画一遍 ​

对应正文：16-ssr-hydration（1 请求链路 / 2 三个入口 / 4 平台差异 / 5 水合一致性 / 7 常见坑）· 配套示例：ssr-lab

剧情回顾 ​

  • 第 1 格：像素酱抱怨首屏白屏、水合后闪一下、点击偶尔没反应。SSR 的收益是首屏内容与 SEO，代价是两端必须画同一份。
  • 第 2 格：码叔拆出三个入口——main.ts 浏览器启动、main.server.ts 服务端引导、server.ts HTTP 服务器；业务代码仍然只有一份。
  • 第 3 格：标签君对照平台差异：服务端没有 window / localStorage，首屏数据用 TransferState 复用，水合前的事件由 withEventReplay() 缓冲。
  • 第 4 格：码叔结案——SSR 不是加速器，是「两端一致」的工程约束；随机值、当前时间、DOM 尺寸都要先固定。

知识点拆解 ​

第 1 格 · 请求链路 ​

一次 SSR 请求依次经过：HTTP 请求 → 服务端引导 → 渲染 HTML → 浏览器先显示 → 下载 JS → 水合 → 接管交互。

任何一步两端结果不一致，就会以闪烁、丢事件或重复请求的形式暴露出来。

第 2 格 · 三个入口 ​

文件运行位置职责
src/main.ts浏览器bootstrapApplication 启动根组件
src/main.server.ts服务端复用同一份引导逻辑
src/server.tsNodeAngularNodeAppEngine 处理请求与静态资源
json
// angular.json
"server": "src/main.server.ts",
"ssr": { "entry": "src/server.ts" },
"outputMode": "server"

构建产物分成 browser/ 与 server/ 两套。

第 3 格 · 平台差异与水合一致性 ​

服务端没有浏览器 API，首屏数据要能从服务端传到浏览器：

ts
// 服务端写入，浏览器读取，避免二次请求
transferState.set(makeStateKey('profile'), profile);
ts
// app.config.ts
provideClientHydration(withEventReplay())

withEventReplay() 会缓冲水合完成前的事件，避免用户早期点击丢失。

第 4 格 · 导致不一致的常见来源 ​

  • 随机数、Date.now()、Math.random() 直接参与渲染；
  • 构造函数里读 window / localStorage；
  • 模块级变量缓存请求状态，跨请求串数据；
  • 服务端与浏览器走不同的数据分支。

需要平台判断时用 isPlatformBrowser() / isPlatformServer()，而不是直接访问 window。

坑点清单 ​

🔗 正文对照：常见坑表格

  1. 模块级缓存请求状态 → 跨请求串数据，改为请求级依赖注入；
  2. 构造函数读 window → 服务端直接崩，改用平台判断或 afterNextRender；
  3. 随机值 / 当前时间直出 → 两端不一致闪烁，先固定再渲染或只在水合后计算；
  4. 忘记 ssr.entry 或 main.server.ts → 构建只出浏览器包，SSR 不生效；
  5. 首屏数据重复请求 → TransferState 已传值仍在浏览器再取一次。

自测 3 题（含答案） ​

  1. SSR 首屏为什么仍需要下载 JS？——服务端只输出 HTML，交互能力仍由浏览器端组件提供；JS 下载并水合后，事件绑定与响应式更新才接管。
  2. withEventReplay() 解决什么问题？——水合完成前用户已经产生的事件会被缓冲，水合后重放，避免早期点击丢失。
  3. 为什么模块级缓存会在 SSR 中出问题？——Node 服务进程被所有请求共享，模块级变量会跨请求保留上一个用户的数据，造成数据串号与泄漏。
