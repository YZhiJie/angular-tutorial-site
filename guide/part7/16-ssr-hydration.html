16 · SSR 与水合 ​

所属：第七篇 · 精通专题　配套示例：ssr-lab（需本地 Node 预览）

学习目标 ​

  • 说清一次 SSR 请求的完整链路：Node 请求 → 服务端引导 → 序列化 HTML → 浏览器水合
  • 能区分 CSR、SSR、预渲染与混合渲染，并说明各自适用的页面
  • 能配置 main.server.ts、app.config.server.ts 与 server.ts 三个入口
  • 能用 PLATFORM_ID、isPlatformServer、REQUEST 处理平台差异
  • 能解释水合不匹配的成因，并用 afterNextRender 把浏览器专属逻辑推迟到水合之后
  • 能说明 SSR 的缓存、安全与可观测性代价，而不是默认「上了 SSR 就更快」

1. 为什么需要服务端渲染 ​

纯客户端渲染（CSR）的首屏要等三件事依次完成：下载 JS、解析执行、发出数据请求。在此之前页面 只有空壳。对内容型页面，这会造成三个问题：首屏空白时间长、爬虫拿不到正文、社交平台抓不到分享 预览。

SSR 把「组件渲染成 HTML」这一步挪到服务端：浏览器拿到响应时正文已经在 HTML 里，JS 到达后再 水合（hydration）——复用已有 DOM，绑定事件与状态，而不是重新渲染一遍。

模式首屏 HTML 含正文何时生成典型场景
CSR否浏览器运行时内部后台、强交互单页
SSR是每次请求个性化首页、详情页
预渲染（SSG/prerender）是构建时博客、文档、营销页
混合渲染按路由决定按路由配置大型站点混合使用

代价同样明确：每个请求都要占用服务端 CPU；缓存与失效策略变复杂；浏览器专属 API 需要显式隔离； 错误会发生在服务器日志里而不是用户控制台。

2. 一次 SSR 请求发生了什么 ​

两个关键点：服务端应用是按请求创建的，不能把请求级状态放进模块级变量；服务端只负责产出 HTML，交互仍然要靠浏览器端应用接管。

3. 三个入口各管什么 ​

示例把配置拆成三份，职责互不重叠：

ts
// 文件：src/main.server.ts
import { BootstrapContext, bootstrapApplication } from '@angular/platform-browser';
import { App } from './app/app';
import { config } from './app/app.config.server';

const bootstrap = (context: BootstrapContext) => bootstrapApplication(App, config, context);

export default bootstrap;
ts
// 文件：src/app/app.config.server.ts
const serverConfig: ApplicationConfig = {
  providers: [provideServerRendering()],
};

export const config = mergeApplicationConfig(appConfig, serverConfig);

app.config.ts 保存浏览器与服务端共用的 provider；app.config.server.ts 只追加服务端能力； main.server.ts 是「如何引导」；server.ts 是「谁来监听端口」：

ts
// 文件：src/server.ts
const engine = new AngularNodeAppEngine({ allowedHosts: ['localhost', '127.0.0.1'] });

export const reqHandler = createNodeRequestHandler(async (req, res, next) => {
  const response = await engine.handle(req);
  if (response) {
    await writeResponseToNodeResponse(response, res);
    return;
  }
  // 引擎不认识静态资源请求，回退到 browser 目录
  next();
});

AngularNodeAppEngine 只处理 Angular 路由；main-*.js、CSS 这类静态资源要由外层服务器提供。 生产环境通常用 Express、Fastify 或 CDN 承担这部分，示例用最小的 node:http 写清楚边界。

angular.json 对应三项配置：

json
"server": "src/main.server.ts",
"ssr": { "entry": "src/server.ts" },
"outputMode": "server"

outputMode: "server" 才会产出 dist/ssr-lab/server/ 与 dist/ssr-lab/browser/ 两套产物。只写 server 而漏掉 ssr.entry，构建会退回到「服务端与渲染逻辑打进同一个 bundle」的旧行为。

4. 平台差异：同一份代码，两种环境 ​

服务端没有 window、document，也不能假设请求一定存在。示例用平台判断与可选注入把差异收在 组件里：

ts
// 文件：src/app/app.ts
private readonly platformId = inject(PLATFORM_ID);
private readonly request = inject(REQUEST, { optional: true });

protected readonly isServer = isPlatformServer(this.platformId);
protected readonly requestUrl = this.request?.url ?? '（浏览器端没有 REQUEST）';

浏览器端 REQUEST 为 null，所以用 optional: true 注入。需要真实 window 的逻辑不要放在 构造函数里，而应放进 afterNextRender：

ts
constructor() {
  // 仅在浏览器、且首屏渲染完成后执行
  afterNextRender(() => this.hydrated.set(true));
}

afterNextRender 在服务端不会执行，在浏览器端也要等首次渲染完成，因此适合做「水合完成」的 观测点，也适合挂载第三方图表、读取 localStorage 等只能在浏览器做的事。

5. 水合匹配：DOM 必须对得上 ​

水合不是重新渲染，而是把浏览器应用「接到」服务端产出的 DOM 上。如果两端结构或文本不一致， Angular 会在开发模式下报 hydration mismatch，并可能丢弃部分 DOM 重新渲染。

常见不匹配来源：

来源例子规避方式
随机值/时间Math.random()、Date.now() 直接进模板服务端生成后通过状态传输，或水合后再更新
浏览器专属 API构造函数里读 window放进 afterNextRender 或 isPlatformBrowser 分支
条件渲染依赖环境服务端判断 UA 决定结构用同一份输入，或把差异放到 CSS
无效 HTML 结构表格里直接放 <div>按 HTML 内容模型写模板

示例把构造时间显示出来，正是为了让你看到「服务端实例」与「浏览器实例」的值不同——这类值如果 直接参与结构判断，就会造成不匹配；只作为文本展示则没有结构风险。

6. 状态传输与事件回放 ​

服务端已经请求过的数据，浏览器端不应该再请求一次。Angular 的做法是把状态序列化进 HTML， 浏览器端从 TransferState 读取。相关能力由 provideClientHydration() 启用，示例在 app.config.ts 中注册：

ts
providers: [
  provideBrowserGlobalErrorListeners(),
  provideClientHydration(withEventReplay()),
];

withEventReplay() 解决的是「JS 还没下载完，用户已经点了按钮」：事件先被记录，水合完成后回放。 没有它，水合前的那次点击会丢失。Angular 22 的增量水合默认随 provideClientHydration 启用， @defer 块可以按需水合；withIncrementalHydration() 已标记废弃。

7. 可运行示例 ​

SSR 与水合实验室

服务端渲染、平台差异与水合一致性检查，需在 Node 环境独立预览。

该示例需要本地运行，不在浏览器沙箱内。

在仓库根目录执行 pnpm --filter ssr-lab build && pnpm --filter ssr-lab serve:ssr， 然后访问 http://localhost:4000。

示例需要 Node 环境，页面内只展示说明与源码。实际验证按以下顺序执行：

bash
pnpm --filter ssr-lab build
pnpm --filter ssr-lab serve:ssr

浏览器打开 http://localhost:4000，然后做三件事：

  1. 右键「查看网页源代码」。验收：HTML 里已经包含「服务端渲染」与构造时间，而不是空的 <app-root>。
  2. 打开 Network 面板刷新。验收：文档请求先返回完整 HTML，main-*.js 随后才下载并执行。
  3. 在 JS 尚未加载完成时点击按钮。验收：开启事件回放后，水合完成时计数会增加，点击不丢失。

8. 代码拆解 ​

服务端引导入口只做一件事：把「共享配置 + 服务端配置」交给 bootstrapApplication。它不包含 任何请求处理逻辑。

ts
// 文件：src/main.server.ts
const bootstrap = (context: BootstrapContext) =>
  bootstrapApplication(App, config, context);

server.ts 的职责是适配 HTTP。注意 engine.handle 返回 null 表示「不是 Angular 路由」， 这时才回退到静态文件；如果直接返回 404，浏览器就永远拿不到 JS。

ts
// 文件：src/server.ts
const response = await engine.handle(req);
if (response) {
  await writeResponseToNodeResponse(response, res);
  return;
}

allowedHosts 是 SSRF 防护的一部分：引擎只接受白名单内的 Host，避免把任意 Host 带进渲染链路。 生产环境还应限制请求体大小、设置超时，并在反向代理层终止 TLS。

9. 常见坑 ​

现象原因处理
首屏仍是空白没有配置 SSR 入口或 outputMode 仍是 static检查 server、ssr.entry、outputMode 三项
页面样式丢失静态资源请求没有被服务外层服务器提供 browser/ 目录或交给 CDN
开发模式报 hydration mismatch两端结构或文本不一致把随机值/时间移出水合路径，或改用状态传输
服务端报 window is not defined构造函数或模块顶层访问浏览器 API用 afterNextRender 或 isPlatformBrowser 隔离
用户点击「没反应」水合尚未完成且没有事件回放加 withEventReplay()
不同用户看到同一份个性化数据把请求状态放进模块单例服务端应用必须按请求创建
服务器 CPU 飙高每个请求都完整渲染且无缓存对稳定页面预渲染或用 CDN/缓存层
node dist/.../server.mjs 启动即退出没有 isMainModule 判断或端口被占用检查启动分支与 PORT 环境变量

10. 练习 ​

  1. 给示例加一个 /about 路由，并在 app.routes.ts 中把它标记为预渲染。验收：构建日志出现 「Prerendered 1 static route」之外的第二个预渲染路由，HTML 在构建时就生成。
  2. 在 app.ts 中增加一个「只在浏览器显示」的区块，用 isPlatformBrowser 控制。验收：查看源 代码时该区块不存在，水合后出现，且没有 mismatch 警告。
  3. 用 REQUEST 读取请求路径并显示出来，分别访问 / 与 /about。验收：服务端输出的 URL 随 请求变化，浏览器端显示兜底文案。
  4. 故意在模板里渲染 Math.random()，观察开发模式的水合警告；然后修复它。验收：你能说出警告 指向的结构位置，并解释修复方案。
  5. 用 curl -s http://localhost:4000/ | wc -c 对比开启/关闭 SSR 时的首屏 HTML 体积。验收：SSR 响应包含完整正文，体积明显大于空壳。

11. 自测 ​

1. SSR、预渲染与 CSR 的边界是什么？

CSR 在浏览器里生成首屏 HTML；SSR 在每次请求时由服务端生成；预渲染在构建时生成并作为静态文件 分发。SSR 适合个性化或实时内容，预渲染适合稳定内容，CSR 适合不依赖首屏内容的后台应用。

2. 为什么服务端应用不能保存请求级状态？

服务端进程会被多个请求复用。如果把当前用户、当前请求放进模块级变量，下一个请求会读到上一个 请求留下的值，造成串数据。请求级状态应放在组件/provider 的请求作用域内，由 Angular 的按请求 引导隔离。

3. afterNextRender 和 ngOnInit 有什么本质区别？

ngOnInit 在服务端也会执行；afterNextRender 只在浏览器端、首屏渲染完成后执行。因此它既能 避开服务端缺失的 DOM API，也天然位于水合之后，适合挂载第三方库或读取浏览器存储。

4. 水合不匹配为什么常常来自「时间」和「随机数」？

服务端渲染时算了一次值并写进 HTML，浏览器端引导时又算了一次，两次结果不同。若这个值参与结构 或文本比较，水合就会认为 DOM 与预期不符。把它挪到水合之后更新，或由服务端算好后传输，就能保持 两端一致。

本章小结 ​

  • SSR 把正文生成提前到服务端，浏览器拿到 HTML 后再水合接管交互。
  • main.server.ts、app.config.server.ts、server.ts 分别负责引导、服务端 provider 与 HTTP。
  • 平台差异用 PLATFORM_ID、isPlatformServer、REQUEST 显式隔离。
  • afterNextRender 是浏览器专属逻辑与水合观测点的正确位置。
  • 水合要求两端 DOM 一致；时间、随机数与浏览器 API 是主要的不匹配来源。
  • 状态传输与事件回放属于水合能力，缓存、安全与成本才是 SSR 的长期代价。
