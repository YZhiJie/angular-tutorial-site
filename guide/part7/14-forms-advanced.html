14 · 表单进阶：FormArray、CVA、异步校验与 Signal Forms ​

所属：第七篇 · 精通专题　配套示例：forms-advanced

学习目标 ​

  • 能用 nonNullable 与类型化表单消除模板里的空值分支
  • 能用 FormArray 表达数量不固定的字段，并正确增删与校验
  • 能实现 ControlValueAccessor，把自定义控件接入 formControlName
  • 能编写带防抖的异步校验器，并处理 PENDING 状态
  • 能说明 Signal Forms 与经典响应式表单的模型差异与迁移边界

1. 从「能校验」到「模型可推理」 ​

基础表单解决的是「输入 → 校验 → 提交」。真实业务还会遇到三类问题：字段数量不固定、控件不是 原生输入、校验依赖远端状态。经典响应式表单用 FormArray、ControlValueAccessor 与异步校验器 分别解决它们；Signal Forms 则把模型与校验规则都放进 signal 图。

先看校验的执行顺序。同步校验器先跑，异步校验器只在同步校验通过后执行；异步期间控件状态是 PENDING，不是 VALID 或 INVALID：

这就是为什么异步校验必须配合 updateOn: 'blur' 或防抖：每次按键都发请求，既浪费网络，也会让 界面在 PENDING 与 INVALID 之间闪烁。

2. 类型化表单与 FormArray ​

示例用 FormBuilder.nonNullable 建表，字段值不再包含 null，模板可以直接读取字符串：

ts
// 文件：src/app/classic-form.ts
protected readonly form = this.fb.nonNullable.group({
  username: this.fb.nonNullable.control('', {
    validators: [Validators.required, Validators.minLength(3)],
    asyncValidators: [usernameTaken()],
    updateOn: 'blur',
  }),
  password: this.fb.nonNullable.control('', [
    Validators.required,
    Validators.minLength(8),
  ]),
  phones: this.fb.nonNullable.array([this.fb.nonNullable.control('')]),
});

FormArray 的关键不是「数组」，而是「每个元素都是独立控件」。增删元素要调用 push / removeAt， 不能直接修改底层数组，否则校验与脏值状态不会更新：

ts
protected addPhone(): void {
  this.form.controls.phones.push(this.fb.nonNullable.control(''));
}

protected removePhone(index: number): void {
  this.form.controls.phones.removeAt(index);
}

模板用 $index 作为 formControlName，因为 FormArray 的键就是数字下标：

html
@for (phone of form.controls.phones.controls; track $index) {
  <div class="row">
    <input [formControlName]="$index" autocomplete="tel" />
    <button type="button" (click)="removePhone($index)">删除</button>
  </div>
}

3. ControlValueAccessor：让自定义控件说表单语言 ​

密码强度输入不是原生 input 的简单包装，但表单仍然要能 setValue、disable、触达 touched。 ControlValueAccessor 就是这层协议：

ts
// 文件：src/app/password-strength.ts
providers: [
  {
    provide: NG_VALUE_ACCESSOR,
    useExisting: forwardRef(() => PasswordStrength),
    multi: true,
  },
],

四个方法各司其职：writeValue 接收表单推来的值，registerOnChange 保存「值变化时通知表单」的 回调，registerOnTouched 保存失焦回调，setDisabledState 响应 disable()。组件内部仍可以用 signal 保存展示状态，但对外必须调用 onChange：

ts
protected onInput(event: Event): void {
  const value = (event.target as HTMLInputElement).value;
  this.value.set(value);
  this.onChange(value);
}

在模板里，自定义控件与原生输入没有区别：

html
<app-password-strength formControlName="password" />

4. 异步校验：延迟、状态与取消 ​

示例的异步校验器模拟「用户名是否被占用」，800ms 后返回结果：

ts
// 文件：src/app/username.validator.ts
export function usernameTaken(): AsyncValidatorFn {
  return (control: AbstractControl): Observable<ValidationErrors | null> =>
    of(String(control.value ?? '')).pipe(
      delay(800),
      map((value) =>
        TAKEN.has(value.trim().toLowerCase()) ? { usernameTaken: true } : null,
      ),
    );
}

模板必须同时处理三种状态：pending、具体错误、以及「还没触碰」不显示错误。示例用 form.controls.username.pending 展示检查中提示，错误只在 touched 后出现：

html
@if (form.controls.username.pending) {
  <p class="muted" role="status">正在检查用户名是否可用...</p>
}
@if (form.controls.username.touched && form.controls.username.hasError('usernameTaken')) {
  <p class="error" role="alert">这个用户名已经被占用。</p>
}

跨字段校验（例如「结束时间必须晚于开始时间」）不适合拆成两个字段级校验器，应挂在 FormGroup 上读取兄弟控件。这样错误可以显示在组级别，也不会因为字段更新顺序产生假阴性。

5. Signal Forms：模型即 signal ​

Signal Forms 把「模型」与「校验 schema」分开：模型是普通 signal，form() 围绕模型建立字段树， 模板用 [formField] 双向绑定。示例的写法如下：

ts
// 文件：src/app/signal-form.ts
protected readonly model = signal({ name: '', email: '', age: 18 });
protected readonly profile = form(this.model, (path) => {
  required(path.name);
  minLength(path.name, 3);
  email(path.email);
  min(path.age, 18);
});

protected readonly snapshot = computed(() => JSON.stringify(this.model()));
html
<input id="signal-name" [formField]="profile.name" />
@if (profile.name().invalid()) {
  <p class="error" role="alert">姓名至少 3 个字符。</p>
}

与经典表单的差异：

维度经典响应式表单Signal Forms
真源FormGroup / FormControl 树普通 signal 模型
校验控件级 Validatorschema 中的规则函数
读取状态control.invalid / errors字段 signal 的 invalid() / errors()
与模板formControlName[formField]

Signal Forms 在 Angular 22 仍属于较新的 API，团队落地前应确认版本与稳定性，并先在小范围表单 试点。它不会自动替换经典表单：需要 FormArray 动态结构、大量既有 Validator 或第三方 CVA 的 场景，经典表单仍然更成熟。

7. 常见坑 ​

现象原因处理
表单值仍可能是 null用了可空控件或未加 nonNullable用 fb.nonNullable 建表，或在模板显式兜底
删除 FormArray 元素后校验错位直接修改底层数组用 push / removeAt / clear
自定义控件不更新表单只改了内部 signal，没调用 onChange在 writeValue 与 onChange 两个方向都实现
异步校验每次按键都触发没有 updateOn 或防抖updateOn: 'blur'，并在校验器内 debounceTime
异步校验期间误判为通过把 PENDING 当成 VALID单独处理 pending 状态，提交按钮可暂时禁用
跨字段错误显示在两个字段上校验器挂在单个控件把校验器挂到 FormGroup，错误在组级别读取
Signal Form 模板不更新[formField] 绑定到了普通对象绑定到 form() 返回的字段树

8. 练习 ​

  1. 为 phones 增加「至少一个电话号码」的组级校验。验收：删空后提交显示组级错误，添加一条后错误消失。
  2. 给密码强度控件增加 aria-describedby，把强度文案与输入框关联。验收：屏幕阅读器能读出「弱/中/强」。
  3. 把异步校验器改为可取消：用 switchMap + timer(800)，快速改值时只保留最后一次结果。验收： 连续输入时 PENDING 不会无限延长，最终只按最后一次值判定。
  4. 在 Signal Forms 中新增「确认邮箱」字段，并写一条跨字段规则要求两者一致。验收：不一致时两个 字段都显示错误，修改一致后错误消失。
  5. 把 snapshot() 改成只显示 name 与 age，观察模板依赖是否仍然只跟随这两个字段。验收：修改 email 时快照不变，说明 computed 的依赖是细粒度的。

9. 自测 ​

1. 为什么 FormArray 不能用普通数组替换？

普通数组没有控件树、校验状态与值变化事件。FormArray 的每个元素都是独立 AbstractControl， 增删必须经过它的 API，才能让父表单重新计算有效性、脏值与值。直接改底层数组会绕过这些通知。

2. ControlValueAccessor 的 onChange 与 writeValue 分别负责什么方向？

writeValue 是表单 → 控件：表单设置值或重置时调用，控件更新内部展示。onChange 是控件 → 表单： 用户输入时调用，把新值推给表单。只实现一个方向，表单与控件就会不同步。

3. 异步校验为什么必须处理 PENDING？

异步校验器返回前，控件既不是有效也不是无效，而是 PENDING。如果把 PENDING 当作 VALID， 用户可能在请求尚未返回时就提交；如果当作 INVALID，又会误报错误。正确做法是单独展示检查中 状态，并在需要时禁用提交。

4. Signal Forms 与经典表单最重要的差异是什么？

Signal Forms 以普通 signal 模型为真源，校验规则集中写在 schema 中，字段状态通过 signal 读取； 经典表单以控件树为真源，校验器挂在控件上。前者更贴近 signal 的依赖模型，后者在动态结构与既有 生态上更成熟。

本章小结 ​

  • nonNullable 与类型化表单让模板少一层空值分支。
  • FormArray 用控件 API 增删元素，下标就是 formControlName。
  • CVA 让自定义控件同时满足「展示」与「表单协议」。
  • 异步校验要配合 blur/防抖，并显式处理 PENDING。
  • Signal Forms 把模型与 schema 放进 signal 图，适合新表单试点，不适合一刀切迁移。
