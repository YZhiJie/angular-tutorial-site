18 · 迁移与架构治理 ​

所属：第七篇 · 精通专题　配套示例：architecture

学习目标 ​

  • 制定 AngularJS → Angular、NgModule → standalone 的分阶段迁移路线
  • 判断哪些代码可以机械迁移，哪些必须重写并补测试
  • 用依赖方向、边界规则与所有权约定约束大型代码库
  • 把版本升级、弃用清理与质量门禁变成可持续的流程
  • 说明迁移中的风险点：双框架运行、路由冲突、状态重复、构建体积回退

1. 迁移不是一次重写 ​

大型应用的迁移失败，通常不是因为技术难，而是因为「一次性重写」：范围失控、无法回归、业务 等不起。可行路线是把迁移拆成可独立验证的阶段，每一阶段都能上线、能回滚。

  • 现状盘点：列出框架版本、路由入口、状态管理、构建方式、测试覆盖与最痛的模块。
  • 测试与门禁：没有回归网就不迁移。至少覆盖关键流程与数据契约。
  • 基础设施先迁：构建、路由、HTTP、国际化这些横切能力先稳定，业务组件才有共同底座。
  • 纵向迁移：按「一个路由 / 一个特性」端到端迁移，而不是按技术层横向切。
  • 清理旧栈：删除双写适配层、旧依赖与兼容开关，避免长期维护两套心智。
  • 约束固化：把依赖方向、目录职责与升级节奏写进 lint、脚本与文档。

2. 常见迁移路线与判断标准 ​

迁移项机械程度主要风险判断标准
AngularJS → Angular低双框架共存、DI 与 digest 差异按路由灰度，先迁只读页面
NgModule → standalone中高共享模块拆分、 provider 作用域变化组件能否独立声明依赖、测试是否可独立运行
构造函数注入 → inject()高继承与初始化顺序构造参数是否被用于非 DI 逻辑
*ngIf / *ngFor → 控制流高模板引用变量、track 语义是否有复杂嵌套与动态模板
手写订阅 → signal / toSignal中双真源、销毁时机状态是否只有一个写入方
Zone.js → zoneless中依赖 Zone 补丁的第三方库是否有库依赖隐式变更检测

机械程度高不代表零风险：批量改写的代价往往藏在「测试没覆盖到的边界」里。迁移顺序应优先选择 「可观测、可回滚、依赖少」的模块。

3. 迁移中的三个结构性坑 ​

双真源。 迁移期常见「signal 与 BehaviorSubject 同时保存同一份状态」。两个写入方会让调试 无从下手。原则是：迁移期间选定一个真源，另一侧只做派生。

Provider 作用域漂移。 NgModule 的 providers 与组件级 providers 在 standalone 下语义 不同。把服务从模块挪到 app.config.ts 时，要确认它不是「每个特性一份实例」的隐式约定。

路由双栈。 AngularJS 与 Angular 路由同时接管 URL，会出现刷新后落到错误应用。灰度方案必须 明确「哪些前缀归新应用」，并在反向代理层做兜底。

4. 架构治理：把依赖方向写死 ​

第 11 章的订单示例已经给出分层：core 提供领域契约与通用能力，features 组织用例，组件只 依赖 Facade，不直接碰请求细节。

治理不是多写文档，而是让违规可失败：

  1. 目录约定：core 不允许 import features；features/a 不允许 import features/b 的内部文件。
  2. 边界 lint：用 ESLint 的 no-restricted-imports 或 Nx 的 module boundaries 固化规则。
  3. 公共出口：每个特性只暴露 index.ts，内部文件不对外可见。
  4. 所有权：每个目录有明确的 owner，跨边界修改需要评审。
  5. ADR：架构决策记录写清背景、选项、结论与失效条件，避免「口口相传」。

规则的价值在于「新增代码默认合规」。如果只能靠 review 记忆，边界迟早被绕过。

5. 版本与弃用治理 ​

Angular 的升级节奏稳定，但每次大版本都会带来弃用项。可持续的做法是把升级变成固定动作，而不是 临时救火：

  • 固定节奏：每个大版本一次升级窗口，先升依赖、再清弃用、最后删兼容代码。
  • 先读弃用清单：升级前用 ng update 的提示与官方弃用列表建立待办，而不是等编译报错。
  • 小步提交：依赖升级与业务改动分开提交，方便定位回归。
  • 门禁兜底：类型检查、模板编译、单元测试、构建预算与沙箱新鲜度都要在 CI 中执行。

本仓库的门禁顺序（check:examples → build:examples → test:examples → docs:build）就是 这个思路的最小版本：先保证示例与文档一致，再保证能构建、能测试、能发布。

7. 常见坑 ​

现象原因处理
迁移后页面偶发空白双路由接管 URL 或懒加载路径错配明确前缀归属，检查 base href 与 fallback
同一状态两处更新signal 与 Subject 双真源选定唯一写入方，另一侧派生
服务出现多份实例provider 作用域从模块挪到根级明确「单例」还是「每特性一份」
批量改写后测试大面积失败机械替换破坏了初始化顺序小步提交，先补测试再迁移
边界规则写了但没人遵守只靠文档与 review用 lint / 脚本让违规构建失败
升级后包体积回退新依赖进入首屏或未清理旧包用构建预算与 stats 产物核对
旧代码长期保留兼容开关迁移没有「清理阶段」给兼容层设定删除日期与 owner

8. 练习 ​

  1. 选一个现有特性，画出它的依赖方向图，标出至少一处反向依赖。验收：你能给出具体的拆分或 接口调整方案。
  2. 为一个目录写 3 条 no-restricted-imports 规则。验收：故意违规时 lint 失败，而不是只给警告。
  3. 写一份 ADR：主题是「状态管理选 signal 还是引入第三方库」。验收：包含背景、选项、结论与 重新评估的条件。
  4. 把一次假想的版本升级拆成 4 个提交：依赖、弃用清理、兼容层删除、文档更新。验收：每个提交 都能独立构建与测试。
  5. 给 architecture 示例增加一个「订单归档」用例，并保持组件不直接依赖仓储。验收：Facade 承担编排，组件只读 signal。

9. 自测 ​

1. 为什么迁移要按特性纵向切，而不是按技术层横向切？

纵向切能把「路由、组件、状态、测试」一次迁完并独立上线，回滚范围小；横向切会让新旧实现长期 并存，同一个页面里同时出现两套模式，风险和心智负担都更高。

2. 迁移期为什么要先建立测试与门禁？

迁移会产生大量机械改动，回归只能靠自动化发现。没有测试与构建门禁，问题会在上线后暴露，修复 成本远高于迁移本身。

3. 边界规则怎样才算「有效」？

能被工具执行、能让违规构建失败，并且新增代码默认满足规则。只写在文档里、依赖 review 记忆的 规则，在人员流动与交付压力下会迅速失效。

4. 什么时候应该删除兼容层？

当旧路径的流量归零、相关测试全部迁移、且没有外部消费者依赖时。删除前应设定明确日期与 owner， 否则兼容层会变成永久技术债。

本章小结 ​

  • 迁移应分阶段推进：盘点、门禁、基础设施、纵向迁移、清理、固化约束。
  • 机械迁移也要小步提交，风险藏在测试未覆盖的边界里。
  • 双真源、provider 作用域与路由双栈是迁移期最常见的结构性问题。
  • 架构治理要让依赖方向「可失败」：目录约定、边界 lint、公共出口与所有权。
  • 版本升级与弃用清理应固定节奏，并由门禁兜底。
