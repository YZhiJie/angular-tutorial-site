15 · 安全边界：净化、CSP 与可信内容 ​

所属：第七篇 · 精通专题　配套示例：i18n-a11y

学习目标 ​

  • 能识别 XSS 的常见入口：innerHTML、动态 URL、事件属性、第三方脚本
  • 能说明 Angular 的自动净化覆盖了什么，以及 bypassSecurityTrust* 的风险
  • 能用 DomSanitizer 显式净化 HTML 与 URL，并解释 SecurityContext 的取值
  • 能区分 CSP、Trusted Types、CSRF 防护各自解决哪类问题
  • 能列出 SSR 与依赖供应链带来的额外攻击面

1. 信任边界：哪些数据可以直达 DOM ​

前端安全的核心不是「过滤坏字符」，而是「划清信任边界」。来自用户、URL、接口、第三方脚本的数据 都属于不可信输入；模板里的静态文案属于可信内容。不可信输入进入 DOM 前必须经过净化或验证。

记住三条底线：

  1. 文本用插值 ，Angular 会转义，不会执行 HTML。
  2. HTML 用 [innerHTML]，Angular 会净化，但只保留安全标签与属性。
  3. 任何 bypassSecurityTrust* 都是「我保证这段内容安全」的声明，必须来自可信来源，且经过审计。

2. Angular 的自动净化做了什么 ​

Angular 对 [innerHTML]、[style]、[src] 等绑定有内建净化。示例显式调用 DomSanitizer， 方便观察净化结果：

ts
// 文件：src/app/app.ts
protected readonly rawHtml = signal(
  '<b>你好</b><img src="x" onerror="alert(1)">',
);

protected readonly safeHtml = computed(
  () => this.sanitizer.sanitize(SecurityContext.HTML, this.rawHtml()) ?? '',
);

输入中的 <b> 会保留，onerror 会被移除。SecurityContext 决定按哪种规则净化：

SecurityContext用途典型输出
HTML富文本片段移除脚本、事件属性与危险标签
URLhref / src危险协议被替换为 unsafe:
STYLE内联样式移除危险 CSS 表达式
SCRIPT脚本内容仅允许可信脚本

示例同时演示 URL 净化：

ts
protected readonly safeUrl = computed(
  () => this.sanitizer.sanitize(SecurityContext.URL, 'javascript:alert(1)') ?? '',
);

结果不会是可点击的 javascript: 链接。注意 sanitize 返回 string | null，必须处理 null， 否则模板会显示空值而不是给出明确兜底。

3. bypassSecurityTrust*：能力越大，责任越大 ​

bypassSecurityTrustHtml、bypassSecurityTrustUrl、bypassSecurityTrustResourceUrl 会跳过净化。 它们只应出现在两种场景：内容来自完全可信的后端富文本服务，或内容已经过独立的 HTML 净化库 （如 DOMPurify）处理。即便如此，也要满足：

  • 内容来源可追溯，不能被普通用户直接写入；
  • 净化库版本持续更新，规则覆盖当前威胁；
  • 输出点有审计与监控，出现异常标签时能告警。

把 bypassSecurityTrustHtml 用在用户评论、昵称、聊天消息上，等同于关闭 XSS 防护。

4. CSP：让「已经进来的脚本」也执行不了 ​

净化解决「恶意内容进入 DOM」，CSP（Content Security Policy）解决「即使脚本进来了，也别执行」。 一个务实的起点是禁止内联脚本与外部未知域：

http
Content-Security-Policy:
  default-src 'self';
  script-src 'self';
  style-src 'self' 'unsafe-inline';
  img-src 'self' data:;
  object-src 'none';
  base-uri 'self';

Angular 的构建器支持生成 CSP 相关的 nonce 配置，但 CSP 必须由真实响应头或 <meta> 下发，不能只写 在文档里。上线前用浏览器 DevTools 的 Console 检查违规报告，再逐步收紧，不要一次性把 script-src 收得太死导致生产白屏。

5. Trusted Types：把字符串挡在 DOM API 之外 ​

Trusted Types 要求 innerHTML、script.src 等危险 sink 只接受经过策略创建的 TrustedHTML， 普通字符串会被浏览器拒绝。它与 CSP 配合，可以把「忘记净化」变成运行时错误，而不是静默执行。

落地顺序通常是：先开 Content-Security-Policy-Report-Only 收集违规，再启用 require-trusted-types-for 'script'，最后把第三方库逐个纳入策略。Angular 的模板与 DomSanitizer 已适配 Trusted Types，但自定义 bypass 代码需要单独审计。

6. CSRF、SSR 与供应链 ​

  • CSRF：cookie 认证的写操作需要 SameSite、CSRF token 或双重提交校验。HttpClient 的 withCredentials 不会自动加 token，必须由拦截器统一注入。
  • SSR：服务端渲染会把用户数据拼进 HTML，任何字符串拼接都可能绕过 Angular 的模板转义。 SSR 场景要复用同一套净化逻辑，并警惕「服务端信任客户端」的假设。
  • 供应链：锁定依赖版本、启用 lockfile 校验、审查 postinstall 脚本、避免来源不明的 CDN 脚本。示例仓库用 pnpm lockfile 与 CI 校验保证依赖可复现。

7.1 建议先改这里 ​

  1. 在「用户输入 HTML」中粘贴 <img src=x onerror="alert(1)">。验收：预览区不弹窗，onerror 被移除，只留下安全内容。
  2. 粘贴 <b>加粗</b><script>alert(1)</script>。验收：加粗保留，script 被移除。
  3. 把 safeHtml 改成 bypassSecurityTrustHtml(rawHtml())。验收：预览区可能执行脚本；你能说明 为什么这种写法只能用于可信来源，且不应出现在用户输入路径。
  4. 把 SecurityContext.URL 改成 SecurityContext.HTML。验收：URL 的净化规则不再适用，理解 context 必须与输出位置匹配。

10. 自测 ​

1. 为什么模板插值 {{ value }} 比 [innerHTML] 更安全？

插值会把值当作文本节点写入，HTML 标签不会被解析；[innerHTML] 会把字符串当 HTML 解析，虽然 Angular 会净化，但攻击面更大。纯文本应始终用插值，只有确实需要富文本时才用 innerHTML。

2. bypassSecurityTrustHtml 在什么情况下可以使用？

只在内容来源完全可信、且已经过独立净化与审计时使用，例如后端受控的富文本模板。用户可写内容、 第三方接口内容、URL 参数都不应使用。使用时还要配合 CSP、Trusted Types 与监控。

3. CSP 与净化分别解决什么问题？

净化阻止恶意内容进入 DOM；CSP 限制即使脚本进入页面也不能执行或外联。两者是纵深防御的不同 层次，不能互相替代。CSP 不能修复已经存在的 XSS 漏洞，净化也不能防住所有注入路径。

4. SSR 为什么需要额外的安全审查？

SSR 在服务端拼接 HTML，若直接用字符串插值而不是模板转义，可能绕过 Angular 的净化。服务端还 可能信任客户端传入的上下文，产生权限或缓存污染问题。SSR 必须复用同一套净化与鉴权逻辑。

本章小结 ​

  • 先划信任边界，再谈净化；不可信输入永不直达 DOM。
  • DomSanitizer 的 context 必须与输出位置匹配，sanitize 可能返回 null。
  • bypassSecurityTrust* 是高风险声明，只用于可信且已审计的内容。
  • CSP 与 Trusted Types 是纵深防御，不是净化的替代品。
  • CSRF、SSR 与依赖供应链都属于安全边界的一部分。
