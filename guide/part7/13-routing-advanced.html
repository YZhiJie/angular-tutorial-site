13 · 路由进阶：守卫、解析器与匹配策略 ​

所属：第七篇 · 精通专题　配套示例：routing-form

学习目标 ​

  • 能区分路由的匹配、激活、离开三个时机，并选对 canMatch / canActivate / canDeactivate
  • 能用返回 UrlTree 的函数式守卫完成重定向，而不是在组件里补救
  • 能用 ResolveFn 在路由激活前准备数据，并通过 withComponentInputBinding 绑定到组件输入
  • 能用 canMatch + loadComponent 实现「按权限决定是否匹配懒加载路由」
  • 能说明 Resolver 与组件内请求的取舍，以及路由测试的基本手段

1. 导航是一条有顺序的判定链 ​

路由不是「点链接 → 换组件」这么简单。一次导航至少经过三个阶段：先匹配 URL 结构，再判断是否允许 激活，最后才创建组件。把校验放在错误的阶段，会出现「组件已经创建才开始检查权限」或「懒加载 chunk 已经下载才发现无权访问」的问题。

三个守卫的职责边界：

时机守卫类型典型用途失败后果
匹配CanMatchFn按权限/特性开关决定路由是否存在该路由被跳过，继续尝试下一条
激活CanActivateFn登录校验、租户校验阻止激活，可返回 UrlTree 重定向
离开CanDeactivateFn未保存表单离开确认阻止导航，停留在当前页面

2. 函数式守卫：把依赖注入留给运行时 ​

示例的 AuthService 用 signal 保存角色，守卫只读取状态，不持有组件引用：

ts
// 文件：src/app/auth.guards.ts
export const authGuard: CanActivateFn = () => {
  const auth = inject(AuthService);
  const router = inject(Router);
  return auth.signedIn() ? true : router.createUrlTree(['/login']);
};

export const adminMatch: CanMatchFn = () => inject(AuthService).role() === 'admin';

inject() 只能在注入上下文中调用，而路由守卫正好由 Router 在注入上下文中执行，所以不需要构造函数 或 @Injectable 包装。返回 UrlTree 比返回 false 更好：false 只会取消当前导航，页面停在原地； UrlTree 会把用户带到登录页，并保留正确的导航历史。

如果校验需要异步（例如调用后端权限接口），守卫可以返回 Observable<boolean | UrlTree> 或 Promise<boolean | UrlTree>。但要控制超时：守卫阻塞的是整次导航，接口挂起会让页面一直空白。

canDeactivate 的写法与前面类似，只是多一个当前组件实例参数：

ts
export const unsavedChangesGuard: CanDeactivateFn<{ dirty: () => boolean }> = (component) =>
  component.dirty() ? confirm('有未保存的修改，确定离开吗？') : true;

3. Resolver：在激活前把数据准备好 ​

resolve 会在组件创建前执行，解析结果可以通过 withComponentInputBinding 直接绑定到组件输入。 示例的用户详情路由这样声明：

ts
// 文件：src/app/app.routes.ts
{
  path: 'user/:id',
  component: UserDetail,
  canActivate: [authGuard],
  resolve: { profile: userResolver },
}

Resolver 读取路由参数，返回一个带延迟的 Observable：

ts
// 文件：src/app/user.resolver.ts
export const userResolver: ResolveFn<UserProfile> = (route) => {
  const id = route.paramMap.get('id') ?? 'unknown';
  const profile = USERS[id] ?? { id, name: `访客 ${id}`, plan: 'free' as const };
  return of(profile).pipe(delay(600));
};

组件不再需要 ActivatedRoute 或 subscribe，resolver 的 key 与 input 名称一致即可：

ts
// 文件：src/app/user-detail.ts
readonly id = input.required<string>();
readonly profile = input.required<UserProfile>();

Resolver 的优点是把「数据未就绪」变成路由层的失败：请求失败时导航不会完成，用户不会看到一个 半成品页面。代价是首屏更慢，且所有数据都必须在路由配置里声明。列表页、可缓存数据适合 Resolver； 需要局部刷新、轮询或用户交互后再加载的数据，仍应留在组件或服务里。

4. canMatch + 懒加载：连 chunk 都不下载 ​

canMatch 比 canActivate 更早执行。示例让 /admin 先尝试匹配管理员路由；身份不足时，这条路由 直接不参与匹配，落到后面的兜底组件：

ts
{
  path: 'admin',
  canMatch: [adminMatch],
  loadComponent: () => import('./admin').then((m) => m.Admin),
},
{ path: 'admin', component: NoAccess },

这带来两个实际收益：非管理员不会下载管理后台的 chunk；兜底页面可以给出明确提示，而不是让用户 看到一个空白的 403。若把 canMatch 换成 canActivate，懒加载 chunk 已经下载，权限校验才执行， 网络与解析成本都浪费了。

嵌套路由与 loadChildren 遵循同一原则：先按结构匹配，再按权限筛选，最后才加载子路由配置。把 canMatch 放在父路由上，可以让整棵子树都不参与匹配。

6. 常见坑 ​

现象原因处理
守卫里 inject 报错在普通函数或组件构造函数外调用守卫函数由 Router 调用，保持函数式写法
未登录时页面停住而不是跳转守卫返回 false返回 router.createUrlTree(['/login'])
Resolver 报错导致白屏没有处理失败分支在 Resolver 内 catchError，或改用组件内加载并展示错误
无权访问仍下载了懒加载 chunk用了 canActivate 而不是 canMatch把权限筛选前移到 canMatch
子路由参数拿不到父路由没有 router-outlet，或参数名不一致检查嵌套结构与 paramMap key
离开页面没有确认只做了 canActivate增加 canDeactivate，在组件上暴露 dirty()
守卫里发请求没有超时导航被无限期阻塞给权限请求加 timeout，失败时回退到拒绝

7. 练习 ​

  1. 新增 /settings 路由，要求登录后才能访问。验收：未登录访问被重定向到 /login，登录后可进入。
  2. 给 UserDetail 增加 canDeactivate，当页面内的备注输入非空时弹出确认。验收：点击其他导航 链接时出现确认框，取消后停留在当前页。
  3. 给 /admin 增加一个 data: { role: 'admin' }，并在管理组件中读取路由数据。验收：组件能显示 当前要求的角色，且不需要额外服务。
  4. 把 userResolver 的 delay(600) 改成 delay(3000)，观察导航期间的表现。验收：你能说明 Resolver 阻塞的是哪一段，以及为什么不应该给所有页面都加 Resolver。

8. 自测 ​

1. canMatch 与 canActivate 的核心区别是什么？

canMatch 在路由匹配阶段执行，失败时这条路由直接不参与匹配，懒加载不会发生；canActivate 在 路由已经匹配后执行，此时组件与 chunk 可能已经准备好。需要「按权限决定路由是否存在」时用 canMatch，需要「匹配后阻止激活并重定向」时用 canActivate。

2. 为什么守卫返回 UrlTree 比返回 false 更好？

false 只是取消这次导航，用户仍停留在原页面，往往不知道自己被拒绝；UrlTree 会把导航改写到 登录页或其他目标，地址栏与导航历史都正确，用户体验与可观测性都更好。

3. Resolver 适合什么数据，不适合什么数据？

适合激活前必须就绪、失败即不应进入页面的数据，例如详情页主体、权限上下文。不适合需要局部刷新、 轮询、用户操作后才加载的数据，也不适合把大量非关键数据塞进首屏，否则会拖慢导航。

4. withComponentInputBinding 解决了什么问题？

它把路由参数、查询参数与 Resolver 数据按名称绑定到组件输入，组件不再需要注入 ActivatedRoute 并手动订阅。输入仍然是 signal，模板与副作用可以继续沿用 signal 的依赖模型。

本章小结 ​

  • 导航分为匹配、激活、离开三个阶段，守卫要放在正确的阶段。
  • 函数式守卫通过 inject 获取依赖，返回 UrlTree 完成可预期的重定向。
  • Resolver 把「数据未就绪」变成路由层问题，配合 withComponentInputBinding 简化组件。
  • canMatch 能在懒加载之前筛选路由，避免无权限用户下载无用 chunk。
