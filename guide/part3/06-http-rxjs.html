06 · RxJS 与 HTTP 数据流 ​

所属：第三篇 · 进阶　配套示例：http-rxjs

学习目标 ​

  • 能用 Subject 把输入事件转换成可组合的数据流
  • 能解释 debounceTime、distinctUntilChanged 各自消除了哪类无效请求
  • 能用 switchMap 取消过期请求，并说明它与 mergeMap 的差异
  • 能把 catchError 放在正确层级，让一次失败不终止整个搜索
  • 能用 takeUntilDestroyed 绑定组件生命周期，避免订阅泄漏
  • 能用 signal 保存请求状态，在模板中渲染加载、兜底与空结果
  • 能用 toObservable / toSignal 在 signal 与 RxJS 之间搭桥，并说明转换的边界

1. 搜索框的问题不是「发请求」，而是「取消请求」 ​

一个朴素的搜索实现会在每次 input 时调用 HttpClient.get。输入「angular」会立刻产生 7 个 请求，它们返回顺序不确定，最后渲染的可能是最早那次的结果。要解决的不是「怎么发」，而是三件事： 少发（防抖与去重）、只认最新（取消旧请求）、失败可恢复（错误不终止流）。

示例把这三件事写成一条管道：输入先进入 Subject，再经过防抖、去重、切换到新请求、错误兜底， 最后才写入 signal。

ts
this.term$
  .pipe(
    debounceTime(300),
    distinctUntilChanged(),
    switchMap((term) => this.userService.search(term)),
    takeUntilDestroyed(this.destroyRef),
  )
  .subscribe((users) => this.users.set(users));

2. 操作符逐个拆开看 ​

Subject：输入端。 它不是 signal，而是一个可手动推送值的多播 Observable。模板事件调用 term$.next(value)，管道订阅它。signal 负责「渲染状态」，Subject 负责「事件流」，两者分工明确。

ts
private readonly term$ = new Subject<string>();

protected onInput(event: Event): void {
  const value = (event.target as HTMLInputElement).value;
  this.term.set(value);
  this.term$.next(value);
}

debounceTime(300)：等待输入停顿。 每次新值到来都会重置计时器，只有 300ms 内没有新输入才向下 发射。它决定「什么时候发请求」，不改变值的数量。

distinctUntilChanged()：跳过相邻重复值。 用户把光标移来移去但没有真正改字时，不会重复请求。 注意它只比较相邻值，不是全局去重。

switchMap：只保留最新内部流。 收到新关键字时，它会退订上一个 search() 返回的 Observable， 再订阅新的。退订会中止底层 HTTP 请求，因此旧响应没有机会覆盖新结果。若换成 mergeMap，所有请求 并发且结果都会到达；concatMap 则排队等待，适合必须按顺序执行的写操作。

catchError 的位置决定流是否存活。 示例把 catchError 放在 switchMap 的投影函数内部，也就是 每个内部请求自己的管道里。请求失败时它返回 of(FALLBACK_USERS)，内部流正常完成，外层 term$ 仍然存活，后续输入还能继续搜索。如果放到 switchMap 外面，一次失败会让整条外层流完成，搜索框 从此「失灵」。

finalize：无论完成、出错还是被取消都会执行。 它被放在内层，所以既能覆盖成功，也能覆盖超时 与取消，用来关闭 loading 最合适。取消旧请求时它同样会运行，这一点在快速输入时会带来状态时序问题， 后文「常见坑」会展开。

takeUntilDestroyed：把订阅绑定到组件生命周期。 它在注入上下文里调用，这里传入显式注入的 DestroyRef。组件销毁时自动退订整条链，不需要手写 ngOnDestroy 和 Subject 作为销毁信号。

服务层只负责传输。 UserService.search() 返回冷 Observable：没人订阅就不发请求，每次订阅都是 一次独立请求。timeout(8000) 把无响应转成错误，map 在客户端完成过滤。

ts
search(term: string): Observable<User[]> {
  return this.http
    .get<User[]>('https://jsonplaceholder.typicode.com/users')
    .pipe(
      timeout(8000),
      map((users) =>
        users.filter((user) => user.name.toLowerCase().includes(term.trim().toLowerCase())),
      ),
    );
}

HttpClient 来自依赖注入。 应用级配置注册 provideHttpClient()，服务里用 inject(HttpClient) 取得实例；手动 new HttpClient() 会绕过拦截器、测试替身与配置。

signal 与 Observable 的边界。 signal 适合表达「当前状态」，RxJS 适合表达「随时间发生的事件」。 两者可以在边界处互相转换：toObservable(signal) 让 signal 进入操作符管道，toSignal(observable) 把结果接回模板可读的 signal。转换必须发生在注入上下文中，toSignal 还应给出 initialValue。

ts
readonly effectiveTerm = toSignal(
  toObservable(this.term).pipe(debounceTime(300), distinctUntilChanged()),
  { initialValue: '' },
);

示例用它显示「实际生效的搜索关键字」：输入框立即回显，只有停顿 300ms 后这个只读 signal 才更新。 注意不要把同一份状态同时做成可写 signal 和可写 BehaviorSubject，否则会出现两个真源，调试时无法 判断哪一个才是最新值。

3.1 建议先改这里 ​

  1. 把 debounceTime(300) 改成 debounceTime(1000)，快速输入多个字符。验收：停顿一秒后才出现 「请求中...」，请求次数明显减少。
  2. 删除 distinctUntilChanged()，反复输入相同关键字并观察浏览器 Network 面板。验收：相同关键字 也会重新发起请求。
  3. 断网或在 Network 面板选择 Offline，然后输入任意关键字。验收：8 秒内进入兜底分支，页面提示 接口不可达，并展示三条本地用户。
  4. 把 FALLBACK_USERS 增加到 5 条，重复离线测试。验收：兜底列表变为 5 条，错误提示仍然只出现 一次。
  5. 快速输入几个字符，观察「实际用于搜索的关键字」。验收：它只在停顿 300ms 后变化，说明 toObservable → debounceTime → toSignal 这条转换链生效。

4. 代码拆解 ​

入口先把事件写入两个地方：signal 用于输入框回显，Subject 用于驱动请求管道。两者同步更新，模板 不需要直接订阅 Observable。

ts
// 文件：src/app/app.ts
protected readonly term = signal('');
protected readonly users = signal<User[]>([]);
protected readonly loading = signal(false);
protected readonly fallback = signal(false);

private readonly effectiveTerm = toSignal(
  toObservable(this.term).pipe(debounceTime(300), distinctUntilChanged()),
  { initialValue: '' },
);

private readonly term$ = new Subject<string>();

toObservable(this.term) 让 signal 的每次写入成为一个流事件，防抖后再由 toSignal 接回只读 signal。它是观察管道节奏的窗口，不参与真正的请求，因此不会造成双重请求。

构造函数里完成整条管道的装配。注意 takeUntilDestroyed 放在最后，它作用于前面所有操作符；subscribe 只负责把最终数组写回 signal。首屏主动推送一个空字符串，因此无需额外调用加载方法。

ts
// 文件：src/app/app.ts
constructor() {
  this.term$
    .pipe(
      debounceTime(300),
      distinctUntilChanged(),
      tap(() => {
        this.loading.set(true);
        this.fallback.set(false);
      }),
      switchMap((term) =>
        this.userService.search(term).pipe(
          catchError(() => {
            this.fallback.set(true);
            return of(FALLBACK_USERS);
          }),
          finalize(() => this.loading.set(false)),
        ),
      ),
      takeUntilDestroyed(this.destroyRef),
    )
    .subscribe((users) => this.users.set(users));

  this.term$.next('');
}

模板用独立分支表达状态：加载中、兜底提示、结果列表。@for 使用 user.id 作为 track 键， @empty 处理过滤后为空的情况。

html
<!-- 文件：src/app/app.html -->
@if (loading()) {
  <p class="status" role="status">请求中...</p>
}
@if (fallback()) {
  <p class="status warn" role="alert">真实接口不可达，已展示本地兜底数据。</p>
}
@for (user of users(); track user.id) {
  <li><strong>{{ user.name }}</strong><span>{{ user.email }}</span></li>
} @empty {
  <li class="empty">没有匹配的用户。</li>
}

5. 常见坑 ​

现象原因处理
每敲一个字符就发一次请求没有防抖或去重加 debounceTime 与 distinctUntilChanged
旧结果覆盖新结果并发请求按返回顺序写入用 switchMap 取消旧内部流
一次失败后搜索框彻底没反应catchError 放在外层，错误使外层流完成把兜底放进 switchMap 的内部管道
组件销毁后仍在写 signal订阅未绑定生命周期用 takeUntilDestroyed(this.destroyRef)
页面一直显示「请求中」错误分支缺少收尾逻辑在内层加 finalize 统一关闭 loading
快速输入时 loading 短暂闪掉被取消请求的 finalize 在新请求开始后执行把 loading.set(true) 移到 switchMap 的投影函数内
模板首帧读到 undefinedtoSignal 没有 initialValue提供初始值，或用 @if 兜底
在方法里调用 toObservable 报注入错误不在注入上下文中移到字段初始化或 runInInjectionContext

6. 练习 ​

  1. 让关键字长度小于 2 时不发请求（空字符串仍加载全部）。验收：输入一个字符时列表保持上一次结果， 输入两个字符后才开始请求；首屏仍然展示全部用户。
  2. 把 debounceTime 改成 800ms，并用计数器记录 switchMap 被调用的次数。验收：连续快速输入 5 个字符，只触发一次搜索。
  3. 临时把 catchError 移到 switchMap 外层，用离线模式触发一次失败，然后再恢复网络并继续输入。 验收：你能观察到外层流终止、后续输入不再产生请求，并解释原因后把代码改回内层。
  4. 修复快速输入时 loading 闪断的问题。验收：新请求发出后 loading 始终为 true，直到最新请求 完成、失败或被取消。
  5. 把 effectiveTerm 的 debounceTime 改成 800ms，但保持请求管道仍为 300ms。验收：两处节奏 分离，说明转换链可以独立调参，而不会复制业务状态。

7. 自测 ​

1. switchMap、mergeMap、concatMap 该怎么选？

switchMap 在新值到来时取消上一个内部流，适合搜索、路由参数等「只认最新」的场景；mergeMap 并发执行且保留所有结果，适合互不依赖的通知或上传；concatMap 按顺序排队，适合必须串行完成的 写操作。选择依据是业务上「旧任务是否还有意义」。

2. 为什么 catchError 放在 switchMap 内层，搜索还能继续？

内层 catchError 只处理某一次请求的错误，并用 of(FALLBACK_USERS) 转成一个正常值，使该内部流 完成。外层 term$ 没有收到错误，因此仍是活跃状态，下一次 next 还会触发新的 switchMap。

3. takeUntilDestroyed 为什么能拿到组件的销毁时机？

它在注入上下文里取得当前组件的 DestroyRef（示例中显式注入并传入），把退订逻辑注册到销毁 回调上。组件销毁时整条管道被退订，HTTP 请求随之中止，signal 也不会再被写入。

本章小结 ​

  • 搜索数据流的关键是少发、只认最新、失败可恢复，而不是简单地调用 get。
  • debounceTime 与 distinctUntilChanged 控制请求数量，switchMap 控制请求的归属。
  • catchError 的层级决定整条流能否在失败后继续工作，finalize 负责统一收尾。
  • takeUntilDestroyed 把订阅生命周期交给组件，避免销毁后的写入与泄漏。
  • toObservable / toSignal 只在状态与事件的边界转换，避免同一份数据出现两个可写真源。
