05 · Signals 与变更检测 ​

所属：第三篇 · 进阶　配套示例：signals-lab

学习目标 ​

  • 能区分 signal 的读取与写入，并用 set / update 完成不可变更新
  • 能用 computed 表达派生状态，并解释它的惰性求值与缓存行为
  • 能用 effect 同步日志等副作用，同时避免写入回环
  • 能判断何时用 linkedSignal 保存可被用户临时覆盖的草稿值
  • 能说明 zoneless 应用里，哪些操作会让视图重新渲染
  • 能用 untracked 切断不希望的依赖，并用 effect 的 onCleanup 释放资源
  • 能区分 afterNextRender 与 effect 的执行时机，并用 toSignal / toObservable 与 RxJS 互操作

1. 状态不是普通字段，而是一张依赖图 ​

在 Angular 22 里，组件的状态可以直接写成 signal。它是一个带依赖追踪能力的容器： 读取时登记依赖，写入时通知所有依赖者。示例把「单价」和「数量」作为两个源信号，再由它们派生出总价与折后价。

ts
import { computed, signal } from '@angular/core';

const price = signal(199);
const quantity = signal(2);
const total = computed(() => price() * quantity());
const discounted = computed(() => Math.round(total() * 0.88));

price.set(299);
console.log(total()); // 598

这段代码里没有手动调用变更检测，也没有订阅。total 之所以能跟着变，是因为它在计算时读取了 price 和 quantity，Angular 记录了这条边。之后任何一次 set 都会把 total 标记为失效， 模板下一次读取时得到新值。这就是「状态驱动视图」的基本模型。

2. 四种原语的实际行为 ​

signal：唯一的写入入口。 set 替换整个值，update 基于旧值计算新值。signal 用 Object.is 比较新旧值，写入相同值不会通知依赖者，因此不必担心重复写入导致多余渲染。

ts
const quantity = signal(2);
quantity.set(3);
quantity.update((value) => value + 1); // 4

computed：惰性、带缓存的派生值。 它不会在依赖变化时立刻计算，而是等下一次被读取才执行； 只要依赖没变，重复读取直接命中缓存。依赖是动态收集的：如果计算函数里存在条件分支，只有本次 实际读到的 signal 才会被登记。

ts
const total = computed(() => price() * quantity());
const label = computed(() => (total() > 500 ? '大额订单' : '普通订单'));

effect：同步副作用。 effect 在组件首次检查时运行一次，之后只要它读取过的 signal 变化就再次 运行。它适合写日志、同步到 localStorage、与第三方 DOM 库同步，不适合承载异步请求，因为 effect 本身没有取消语义。更重要的是：不要在 effect 里写回它自己读取的状态，否则会形成「写入 → 重跑 → 再写入」的回环。

ts
effect(() => {
  const summary = `总价 ${total()} 元`;
  this.effectLog.update((list) => [...list.slice(-4), summary]);
});

linkedSignal：可写、但会跟随源信号的派生值。 普通 computed 是只读的；linkedSignal 允许 用户修改，而当源信号变化时它会重新计算，把草稿重置。示例用它实现「草稿数量」：用户可以拖动草稿， 只有点击「应用草稿」才写回正式数量；一旦正式数量变化，草稿自动跟随。

ts
const quantityDraft = linkedSignal(() => quantity());
quantityDraft.set(7); // 合法：草稿暂时偏离正式值
quantity.set(5);      // 源变化，草稿重新变为 5

zoneless 下的刷新路径。 Angular 22 默认不依赖 Zone.js。signal 在模板中被读取时，视图会登记 依赖；signal 变化后调度器标记对应组件并刷新。除此之外，模板事件回调、markForCheck()、异步管道 的发射也会触发检查。直接修改对象的属性、往数组里 push，都不会被感知——这是从旧版「事件后全量 检查」迁移过来时最容易踩空的地方。

untracked：读取但不建立依赖。 有些读取只是为了记录或比较，不应该让当前计算跟着它重跑。 untracked 会临时关闭依赖收集：

ts
effect(() => {
  const total = this.total();                       // 依赖：total
  const draft = untracked(() => this.quantityDraft()); // 读取草稿，但不依赖它
  this.snapshot.set(`总价 ${total}，草稿 ${draft}`);
});

上面的 effect 只在 total 变化时重跑；用户拖动草稿不会触发它。若去掉 untracked， effect 会同时依赖 quantityDraft，草稿每动一次就重跑一次。

effect 的清理与渲染时机。 effect 可以接收 onCleanup，在下次执行前或组件销毁时释放资源； afterNextRender 则只在浏览器完成首次渲染后执行一次，适合测量 DOM 尺寸、初始化第三方库。 服务端渲染时 afterNextRender 不会执行，这也是它比 setTimeout(0) 更可靠的原因。

ts
effect((onCleanup) => {
  const timer = setInterval(() => this.elapsed.update((value) => value + 1), 1000);
  onCleanup(() => clearInterval(timer));
});

afterNextRender(() => {
  this.renderLog.set('首次渲染完成');
});

signal 与 RxJS 的双向桥接。 toSignal 把 Observable 接进 signal 图，模板可以直接读取； toObservable 把 signal 变成 Observable，便于复用 RxJS 的防抖、切换与重试操作符。两者都必须在 注入上下文中调用，toSignal 还应提供 initialValue，否则模板在首帧会读到 undefined。

ts
readonly heartbeat = toSignal(interval(1000), { initialValue: 0 });
readonly effectiveTerm = toSignal(
  toObservable(this.term).pipe(debounceTime(300), distinctUntilChanged()),
  { initialValue: '' },
);

桥接不是「二选一」：状态仍以 signal 为真源，只在需要 RxJS 操作符的边界上转换，避免同一份状态 出现两个可写副本。

  2. 把 discounted 里的 0.88 改成 0.5。验收：折后价立刻变为总价的一半，日志里的两个数字 仍然成对更新。
  3. 只拖动「草稿数量」，不要点「应用草稿」，然后拖动正式数量。验收：草稿滑块被重置为正式数量， 说明 linkedSignal 跟随了源信号。
  4. 把 effect 中的 slice(-4) 改成 slice(-9)。验收：日志最多保留 10 条，之前的记录被丢弃。
  5. 观察「RxJS 心跳」每秒递增，再刷新页面。验收：数字从 0 开始重新计数，说明 toSignal 的订阅 绑定在组件生命周期内，没有泄漏到页面之外。
  6. 把 afterNextRender 改成 afterEveryRender，并在回调里 console.log。验收：每次视图刷新都会 打印，而原版只在首次渲染后打印一次。

4. 代码拆解 ​

先看源状态与派生状态的定义。两个 signal 是唯一可写状态，三个 computed 与 linkedSignal 都 是从它们派生出来的，写入路径非常清晰。

ts
// 文件：src/app/app.ts
protected readonly price = signal(199);
protected readonly quantity = signal(2);

protected readonly total = computed(() => this.price() * this.quantity());
protected readonly discounted = computed(() => Math.round(this.total() * 0.88));

protected readonly quantityDraft = linkedSignal(() => this.quantity());

effect 只做一件事：把当前计算结果追加到日志里，并用 slice(-4) 截断。日志本身是一个独立 signal，effect 读取 total 与 discounted，写入 effectLog，读写集合没有交集，因此不会自激。

ts
// 文件：src/app/app.ts
constructor() {
  effect(() => {
    const summary = '总价 ' + this.total() + ' 元，优惠价 ' + this.discounted() + ' 元';
    this.effectLog.update((list) => [...list.slice(-4), summary]);
  });
}

跨界的两个字段放在类初始化位置，因为 toSignal 需要在注入上下文中运行。interval 是冷流， 只有 toSignal 订阅后才开始计时；组件销毁时订阅随之释放。

ts
// 文件：src/app/app.ts
protected readonly heartbeat = toSignal(
  interval(1000).pipe(map((tick) => tick + 1)),
  { initialValue: 0 },
);

protected readonly renderLog = signal('等待首次渲染');

// 构造函数内
afterNextRender(() => {
  this.renderLog.set('首次渲染完成于 ' + new Date().toLocaleTimeString('zh-CN'));
});

afterNextRender 的回调发生在 DOM 已经可测量之后，因此它比在构造函数里读取元素尺寸安全。

事件处理器负责把 DOM 的字符串转成数字，再写入 signal。注意这里用的是 set，而不是修改某个 对象字段；对 signal 来说，写入动作本身就是通知。

ts
// 文件：src/app/app.ts
protected setPrice(event: Event): void {
  this.price.set(Number((event.target as HTMLInputElement).value));
}

protected setQuantity(event: Event): void {
  this.quantity.set(Number((event.target as HTMLInputElement).value));
}

protected applyDraft(): void {
  this.quantity.set(this.quantityDraft());
}

模板侧只做读取和绑定。范围输入用 [value] 回写当前值，(input) 触发事件；草稿滑块直接调用 quantityDraft.set(...)，这是 linkedSignal 可写性的体现。列表用 @for，并以 $index 作为 track 键，因为日志行没有天然唯一 id。

html
<!-- 文件：src/app/app.html -->
<input id="price" type="range" min="50" max="500" step="10"
  [value]="price()" (input)="setPrice($event)" />

<input id="draft" type="range" min="1" max="20" [value]="quantityDraft()"
  (input)="quantityDraft.set(Number($any($event.target).value))" />

@for (line of effectLog(); track $index) {
  <li>{{ line }}</li>
}

5. 常见坑 ​

现象原因处理
修改对象属性后页面不更新zoneless 不会监听任意属性写入用 set / update 替换值，或改为不可变更新
以为 computed 会主动推送新值computed 惰性求值，只有被读取才计算把「展示」交给模板读取，把「副作用」交给 effect
effect 日志无限增长或重复effect 读取并写入了同一个 signal拆分源状态与日志状态，保证读写集合不相交
草稿值在源信号变化后被覆盖linkedSignal 的设计就是跟随源信号预期行为；若要永久保留，另建独立 signal 并显式合并
模板里调用方法导致频繁计算每次检查都会重新执行方法用 computed 缓存派生结果
在 effect 中发 HTTP 请求effect 没有取消与重试语义用 RxJS 或资源类 API 管理异步
effect 里的定时器越来越多没有在清理函数中释放用 onCleanup(() => clearInterval(timer))
只想读一次状态，effect 却反复重跑读取发生在依赖收集区用 untracked 包住这次读取
模板首帧拿到 undefinedtoSignal 没有 initialValue 且源尚未发射提供 initialValue，或改用 @if 兜底
在普通函数里调用 toSignal不在注入上下文中放到字段初始化、构造函数或 runInInjectionContext 中

6. 练习 ​

  1. 新增 shipping = signal(12)，让页面显示「含运费总价」。验收：运费计入总价与折后价， effect 日志随之更新，调整单价时结果正确。
  2. 把固定折扣改成 rate = signal(0.12)，并增加一个 0.5 到 1 的滑块控制「折扣力度」。 验收：折后价随滑块变化，且不会出现负数。
  3. 用 linkedSignal 为单价也做一个草稿，并添加「重置草稿」按钮。验收：正式单价变化后草稿自动 回到正式值；点击重置也能回到正式值。
  4. 给日志加上递增序号，并把上限改为 3 条。验收：每行形如「#7 总价 398 元，优惠价 350 元」，最多显示 3 行。
  5. 把模板里的 total() 改成一个 getTotal() 方法，观察并解释差异。验收：功能不变，但你能说明 为什么方法版本无法享受 computed 的缓存。
  6. 给 quantityDraft 增加一个「上次草稿」记录：在 effect 中用 untracked 读取草稿并写进另一个 signal。验收：正式数量变化时记录更新，拖动草稿时 effect 不重跑。
  7. 把心跳改成 toSignal(interval(1000), { initialValue: -1 })，并在模板用 @if 处理未初始化状态。 验收：首帧不出现 undefined，一秒后开始正常递增。

7. 自测 ​

1. computed 和普通 getter 的核心区别是什么？

computed 会登记依赖并在依赖不变时返回缓存值，只有依赖变化后的首次读取才重新计算；普通 getter 每次被访问都会执行。因此在模板中频繁读取时，computed 能避免重复计算，也能作为稳定的依赖节点 参与后续派生。

2. 为什么不能在 effect 里写回它自己读取的 signal？

effect 的调度依据就是「读取过的 signal 发生变化」。写入同一个 signal 会让 effect 再次满足运行 条件，形成回环，轻则日志重复、重则不断调度。正确做法是把副作用目标做成独立的 signal，或者用 untracked 读取不希望在依赖图中出现的值。

3. linkedSignal 与 computed 的适用场景有何不同？

computed 只读，适合纯派生；linkedSignal 可写，适合「默认跟随源信号、但允许用户临时覆盖」的 草稿场景。源信号变化时 linkedSignal 会重置，这一点与普通 signal 有本质区别。

4. zoneless 下，哪些操作能触发视图刷新？

模板读取的 signal 发生变化、模板事件回调执行、调用 markForCheck()、异步管道发射值等都会触发 调度。直接修改对象属性或数组内容不在其中，所以状态更新要经过 signal 的写入 API。

本章小结 ​

  • signal 把「值 + 依赖关系」放在一起，写入即通知，读取即登记依赖。
  • computed 惰性且带缓存，适合所有纯派生；effect 只负责同步副作用。
  • linkedSignal 解决「跟随源信号但允许临时编辑」的草稿问题。
  • zoneless 下刷新由 signal 通知和模板事件驱动，原地修改对象不会生效。
  • untracked 控制依赖边界，onCleanup 负责释放 effect 资源，afterNextRender 处理首帧后的 DOM 工作。
  • toSignal / toObservable 只在边界处转换，状态仍应保持单一真源。
