09 · 大列表性能调优 ​

所属：第五篇 · 深度　配套示例：perf-lab

学习目标 ​

  • 说清大列表卡顿的三段成本，并能用 performance.now() 量化其中的过滤耗时
  • 用 computed 缓存过滤结果，避免模板在每轮变更检测中重复计算
  • 用 track 为每行建立稳定身份，让 DOM 节点可以复用
  • 用 OnPush 缩小检查范围，用 content-visibility 跳过视口外的布局与绘制
  • 在 DevTools 中区分脚本耗时与布局耗时，判断一项优化是否真的生效

1. 列表为什么会卡 ​

一个 5000 行的列表，每次输入关键词都卡一下，成本通常来自三段：

  1. 脚本成本：对 5000 条数据重新执行 filter 和字符串匹配。
  2. 模板成本：变更检测期间，模板里的表达式和行组件被反复求值。
  3. 浏览器成本：上千个 DOM 节点参与布局与绘制，滚动时持续掉帧。

最常见的错误是把过滤写成模板方法，于是每一轮变更检测都重算一次：

ts
// 反例：模板每次求值都会重新过滤全量数据
protected filtered(): Row[] {
  return this.rows().filter((row) => row.label.includes(this.keyword()));
}

另一个隐蔽问题是 track $index。@for 要求必须写 track，写错不会报错，却会让「第 3 行」的身份随数据顺序漂移，输入框内容、动画状态都会串行。

示例把这三段成本拆开处理：过滤交给 computed，身份交给 track row.id，渲染范围交给 OnPush 与 CSS 的 content-visibility。这样优化点各自独立，也便于逐项测量。

2. 机制拆解 ​

2.1 computed 是带缓存的派生状态 ​

ts
protected readonly visibleRows = computed(() => {
  const keyword = this.keyword().trim();
  const group = this.activeGroup();
  return this.rows().filter(
    (row) =>
      (group === -1 || row.group === group) &&
      (keyword === '' || row.label.includes(keyword)),
  );
});

computed 是惰性的：第一次被读取时才执行，之后把结果缓存起来。它记录执行期间读取过的 signal（keyword、activeGroup、rows），只有这些依赖变化才失效；模板中多次读取 visibleRows() 也只付出一次过滤成本。派生值必须保持纯函数，不要在 computed 里发请求、写 signal 或读 DOM。

2.2 track 决定节点复用 ​

html
@for (row of visibleRows(); track row.id) {
  <li>{{ row.label }}</li>
}

track 告诉框架「这一行的身份是什么」。按 id 追踪时，过滤前后的同一行会被识别为同一个节点，DOM 被移动而不是销毁重建；track $index 则把身份绑定到位置，顺序一变就整体错位。

2.3 OnPush 缩小检查范围 ​

示例组件声明 changeDetection: ChangeDetectionStrategy.OnPush。在 zoneless 下，OnPush 视图只在以下情况被检查：模板事件触发、signal 依赖变化、AsyncPipe 发出新值、显式调用 markForCheck()，或祖先视图被检查且本视图被标记为脏。本例的点击与输入都会写入 signal，因此视图会正常刷新；列表项没有输入属性，父组件刷新时不会重复检查每一行的绑定。

2.4 content-visibility 跳过视口外的渲染 ​

css
.rows li {
  content-visibility: auto;
  contain-intrinsic-size: 44px;
}

content-visibility: auto 让浏览器跳过视口外元素的布局与绘制。contain-intrinsic-size 提供一个占位高度，避免滚动条在元素进入视口时跳动。它不减少 DOM 数量，但能把「渲染成本」从全量降到可视区附近。行高差异很大或必须精确控制渲染窗口时，可改用虚拟滚动（如 Angular CDK 的 cdk-virtual-scroll-viewport）；本示例没有引入额外依赖。

2.5 测量要落在真实区间 ​

ts
const start = performance.now();
this.activeGroup.set(group);
const count = this.visibleRows().length;
const elapsed = performance.now() - start;

performance.now() 返回高精度时间戳，适合测量同步代码块。若要区分「过滤」与「渲染」，用 performance.mark() 与 performance.measure() 打点，在 Performance 面板的 Timings 轨道查看；单次测量可能被计时器精度放大，建议连续执行多次取中位数。

3.1 建议先改这里 ​

  1. 把 Array.from({ length: 5000 } 改成 50000，再点「分组 3」。预期：耗时数字明显上升，但页面不应长时间冻结；如果出现卡顿，用 Performance 面板确认 Long Task 落在脚本还是布局。
  2. 把 track row.id 改成 track $index。预期：静态数据下视觉无变化；在任意行内加一个 <input> 并输入内容，再切换分组，会看到输入内容跟着位置走而不是跟着行。
  3. 注释掉 .rows li 中的 content-visibility 与 contain-intrinsic-size。预期：滚动条总高度基本不变，但滚到底部时 Layout 与 Paint 时间上升。
  4. 把 selectGroup 中的 performance.now() 换成 performance.mark('filter-start') 与 performance.measure('filter', 'filter-start', 'filter-end')，在 Performance 面板里对比两种观测方式。

4. 代码拆解 ​

4.1 数据源与派生状态 ​

ts
// 文件：src/app/app.ts
private readonly rows = signal<Row[]>(
  Array.from({ length: 5000 }, (_, index) => ({
    id: index + 1,
    label: '记录 #' + (index + 1),
    group: index % 5,
  })),
);

protected readonly keyword = signal('');
protected readonly activeGroup = signal(-1);
protected readonly elapsed = signal(0);

rows 设为 private，因为外部只需要读派生结果；keyword、activeGroup、elapsed 设为 protected，供模板绑定。过滤逻辑见 2.1，两个筛选条件合并在一次遍历里完成。

4.2 一次点击完成过滤与测量 ​

ts
// 文件：src/app/app.ts
protected selectGroup(group: number): void {
  const start = performance.now();
  this.activeGroup.set(group);
  // 读取 computed 触发实际过滤，用耗时量化优化前后的差异
  const count = this.visibleRows().length;
  this.elapsed.set(Math.round((performance.now() - start) * 100) / 100 + ' ms / ' + count + ' 行');
}

测量起点放在写入 signal 之前，终点在首次读取 visibleRows() 之后，因此覆盖了「写 signal + 缓存失效 + 真正过滤」的完整路径。结果保留两位小数，避免界面出现过长的浮点数。

4.3 模板中的两层循环 ​

html
<!-- 文件：src/app/app.html -->
@for (group of [0, 1, 2, 3, 4]; track group) {
  <button type="button" [class.active]="activeGroup() === group" (click)="selectGroup(group)">
    分组 {{ group }}
  </button>
}

<ul class="rows">
  @for (row of visibleRows(); track row.id) {
    <li>
      <span>{{ row.label }}</span>
      <span class="group">分组 {{ row.group }}</span>
    </li>
  }
</ul>

css
/* 文件：src/app/app.css */

5. 常见坑 ​

现象原因处理
输入关键词时整页明显卡顿模板调用 filter() 方法，每轮变更检测都重算改成 computed，让依赖不变时复用缓存
删除中间一行后输入框内容串到别的行track $index 把身份绑定到位置用稳定主键 track row.id
OnPush 组件手动 push 数组后页面不更新引用未变，signal 未收到新值用 update 返回新数组，或直接写 signal
滚动条在长列表上抖动content-visibility 缺占位高度设置接近真实行高的 contain-intrinsic-size
过滤耗时显示 0 ms计时精度不足或过滤量太小提高数据量，或连续执行多次取中位数
computed 读不到外部普通变量普通字段不是响应式依赖把依赖改成 signal，或显式传入参数

6. 练习 ​

  1. 增加分组统计：在工具栏旁显示每个分组的行数，用一次遍历生成统计结果。 验收：切换分组与输入关键词时统计数字同步变化，且模板中不出现方法调用。
  2. 支持排序：增加「按名称倒序」开关，把排序并入 computed，不要修改原始 rows。 验收：切换排序后顺序改变，但 rows 的引用与内容保持不变，证明派生状态未被原地修改。
  3. 测量渲染：在列表渲染完成后用 performance.mark() 记录一次时间点，与过滤耗时分开显示。 验收：页面上能同时看到「过滤」与「渲染」两个数字，且过滤数字不包含渲染时间。
  4. 限量渲染：增加「只显示前 200 行」的开关，并保留总命中数提示。 验收：开启后 DOM 行数明显减少，顶部仍显示完整命中总数。

7. 自测 ​

1. computed 的缓存什么时候失效？

当执行期间读取过的任一 signal 被写入时失效。失效不等于立刻重算，而是标记为脏，下一次读取才重新执行。示例中 keyword 或 activeGroup 变化都会让 visibleRows 失效。

2. 已经用了 OnPush，为什么还需要 track？

两者解决的问题不同。OnPush 决定「哪些组件需要检查」，track 决定「列表更新时哪些 DOM 节点可以复用」。没有稳定 track，即使组件不重复检查，节点也会被销毁重建，焦点、输入值、动画状态都会丢失。

3. content-visibility 能减少 JavaScript 执行吗？

不能。它作用于浏览器的布局与绘制阶段，减少视口外元素的渲染工作；数据过滤、模板求值和 DOM 数量都不变。要减少 DOM 数量，需要分页、窗口化或虚拟滚动。

4. 为什么建议把测量起点放在写 signal 之前？

写 signal 会使 computed 失效，真正的过滤发生在下一次读取。如果从读取处开始计时，就漏掉了 signal 写入与依赖失效的开销；从写入前开始，才覆盖用户感知的完整同步路径。

本章小结 ​

  • 大列表卡顿要拆成脚本、模板、浏览器三段分别处理，不要只盯一个指标。
  • computed 提供懒执行与缓存，适合表达过滤、排序、聚合这类派生状态。
  • track 用稳定主键建立身份，是列表正确性与性能的共同前提。
  • OnPush 缩小检查范围，content-visibility 缩小渲染范围，两者互补而非替代。
  • 测量要落在真实链路上，并把过滤与渲染的耗时分开观察。
