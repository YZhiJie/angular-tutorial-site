03 · 依赖注入与服务 ​

所属：第二篇 · 基础　配套示例：di-service

学习目标 ​

  • 能解释 @Injectable({ providedIn: 'root' }) 的根级单例语义。
  • 会在组件与服务中用 inject() 获取依赖，并区分注入上下文的边界。
  • 会用 InjectionToken 注入配置，并通过 optional 提供兜底值。
  • 能在服务里用 signal、computed 与 asReadonly 封装共享状态。
  • 能判断状态应放在组件还是服务，并避免多实例导致的“不同步”。

1. 依赖注入解决的三个问题 ​

1.1 服务是共享状态与逻辑的边界 ​

把计数逻辑放在组件里，两个并列组件各自持有一份 count，互不相通。把状态提升到服务后，两个组件注入的是同一个实例：一个按钮修改，另一个面板立即读到新值。服务同时收拢了“改计数必须记日志”这类业务约束，组件只负责展示与触发。

1.2 注册：providedIn 决定生命周期 ​

ts
// 文件：src/app/counter-store.ts（节选）
import { Injectable } from '@angular/core';

@Injectable({ providedIn: 'root' })
export class CounterStore {}

providedIn: 'root' 表示由根注入器按需创建，整个应用共享一个实例，且没有组件使用时可以被摇树移除。若把 CounterStore 写进某个组件的 providers，该组件及其子组件会得到另一份实例，状态就不再全局同步。

1.3 获取：用 inject() 表达依赖 ​

ts
// 文件：src/app/counter-panel.ts（节选）
export class CounterPanel {
  // 与 LogPanel 拿到的是同一个根级实例
  protected readonly store = inject(CounterStore);
}

inject() 必须在注入上下文中调用：字段初始化器、构造函数或工厂函数都可以。放到按钮回调、setTimeout 或普通方法里会抛出错误，因为那时 Angular 已经离开当前注入器的作用域。字段初始化写法比构造函数参数更简洁，也不会破坏类型推断。

1.4 配置：InjectionToken 承载非类依赖 ​

字符串、数字、配置对象没有类可以充当令牌，需要用 InjectionToken：

ts
// 文件：src/app/logger.ts（节选）
import { InjectionToken } from '@angular/core';

export const LOGGER_PREFIX = new InjectionToken<string>('日志前缀');

在应用配置里注册 { provide: LOGGER_PREFIX, useValue: '[演示]' }，使用时允许缺省。optional: true 让令牌缺失时返回 null 而不是抛 NullInjectorError；Logger 用空值合并运算符回退到默认前缀，因此把 provider 删掉仍能运行。

1.5 服务内用 signal 封装状态 ​

ts
// 文件：src/app/counter-store.ts（节选）
private readonly state = signal(0);
readonly count = this.state.asReadonly();
readonly double = computed(() => this.count() * 2);

increase(step = 1): void {
  this.state.update((value) => value + step);
}

state 私有，外部只能读 count；asReadonly 返回的 signal 没有 set / update，从类型层面阻止越权写入。double 是 computed，随 count 自动重算。服务之间同样用 inject(Logger) 组合，而不是 new Logger()，否则日志实例不会被共享。

2. 动手步骤 ​

bash
cd examples/di-service
npm start

打开 http://localhost:4200，按顺序做三个实验：

  1. 点击左侧“+10”，右侧日志立即新增一条，两倍值 同步变化。这说明 CounterStore 与 Logger 都是根级单例：CounterStore 调用的 Logger 正是 LogPanel 注入的那个实例。
  2. 打开 src/app/app.config.ts，把 useValue 改成 '[我的前缀]'，保存后点击按钮，新日志使用新前缀。
  3. 把 LOGGER_PREFIX 的 provider 整行删除，日志回退为 [app]，验证 optional 与默认值生效。

关键文件职责：

  • counter-store.ts：根级状态服务，负责计数、派生值与日志调用。
  • logger.ts：日志服务与 LOGGER_PREFIX 令牌，保存日志条目。
  • counter-panel.ts / log-panel.ts：两个消费者，各自注入所需服务。
  • app.config.ts：应用级 provider，决定令牌的实际值。

4. 代码拆解 ​

4.1 CounterStore：根级状态与派生值 ​

ts
// 文件：src/app/counter-store.ts
import { Injectable, computed, inject, signal } from '@angular/core';
import { Logger } from './logger';

@Injectable({ providedIn: 'root' })
export class CounterStore {
  // 服务之间同样通过 inject() 组合，而不是手工 new
  private readonly logger = inject(Logger);
  private readonly state = signal(0);

  readonly count = this.state.asReadonly();
  readonly double = computed(() => this.count() * 2);

  increase(step = 1): void {
    this.state.update((value) => value + step);
    this.logger.log('count -> ' + this.state());
  }

  reset(): void {
    this.state.set(0);
    this.logger.log('count 重置为 0');
  }
}

state 是私有可写 signal，count 是公开只读视图，double 由 computed 派生。increase 的 step 有默认值 1，模板传 10 时使用实参。每次写入后立刻调用 logger.log，把“状态变更必须留痕”封装在服务内部，消费者无法绕过。

4.2 Logger：令牌配置与不可变更新 ​

ts
// 文件：src/app/logger.ts
import { Injectable, InjectionToken, inject, signal } from '@angular/core';

// InjectionToken 用来注入非类依赖（配置、常量、接口实现）
export const LOGGER_PREFIX = new InjectionToken<string>('日志前缀');

@Injectable({ providedIn: 'root' })
export class Logger {
  private readonly prefix = inject(LOGGER_PREFIX, { optional: true }) ?? '[app]';
  readonly entries = signal<string[]>([]);

  log(message: string): void {
    this.entries.update((list) => [...list, this.prefix + ' ' + message]);
  }

  clear(): void {
    this.entries.set([]);
  }
}

prefix 在字段初始化时完成注入，缺失时回退到 [app]。log 用展开运算符生成新数组再 update，而不是 push 原数组——signal 只有在写入新引用时才通知消费者。clear 用 set([]) 一次性清空，模板会同步移除列表项。

4.3 消费者与应用级 provider ​

ts
// 文件：src/app/log-panel.ts（节选）
export class LogPanel {
  protected readonly logger = inject(Logger);
}

CounterPanel 的结构完全相同，只是注入 CounterStore。两个组件都没有 providers，因此都向根注入器请求依赖，拿到同一份实例。app.config.ts 里的 { provide: LOGGER_PREFIX, useValue: '[演示]' } 在任何组件创建之前完成注册，Logger 首次被注入时就能读到该值。

5. 常见坑 ​

现象原因处理
两个面板状态不同步各自 new CounterStore()，或在多个组件重复声明 providers使用 providedIn: 'root'，只在根级或共同父级提供
报 NullInjectorError（找不到令牌）InjectionToken 没有注册，且未加 optional在 appConfig.providers 用 useValue 注册，或注入时声明 optional
日志数组更新后界面不变直接 push 原数组，引用未变化用 update 返回新数组
外部代码能直接改服务状态公开了可写 signal暴露 asReadonly()，写入方法留在服务内部

6. 练习 ​

  1. 增加递减：给 CounterStore 添加 decrease(step = 1) 并记录日志。验收标准：count 与 double 同步下降，日志新增一条，CounterPanel 出现对应按钮。
  2. 验证可选令牌：临时删除 LOGGER_PREFIX 的 provider。验收标准：应用不报错，日志以 [app] 开头；恢复后以 [演示] 开头。
  3. 暴露日志条数：在 CounterStore 中用 computed 读取 logger.entries().length 并在面板显示。验收标准：每次操作数字递增，清空日志后归零。
  4. 制造多实例：在 App 中注入 CounterStore 并显示 store.count()，再给 CounterPanel 添加 providers: [CounterStore]。验收标准：点击按钮后顶部计数不动、面板计数变化，说明面板拿到了独立实例；删掉 providers 后两者同步。

7. 自测 ​

1. providedIn: 'root' 与组件 providers 有什么本质区别？

前者由根注入器创建并缓存，整个应用共享一个实例，且可被摇树优化；后者由组件注入器创建，每个组件实例各有一份，作用域限定在该组件及其子组件。共享状态应放在根级。

2. 为什么配置项要用 InjectionToken，而不是字符串令牌？

字符串令牌没有类型信息，容易与其他库的令牌重名；InjectionToken<T> 带泛型，注入结果有静态类型检查，并且对象身份唯一，不会意外碰撞。

3. 服务里的 signal 为什么要 asReadonly？

直接暴露可写 signal，任何消费者都能调用 set / update，状态变更会绕过服务内的日志与校验。asReadonly 只保留读取能力，把写入口收敛到服务方法，便于维护不变量。

本章小结 ​

  • providedIn: 'root' 提供应用级单例；组件级 providers 会产生独立实例，按共享范围选择。
  • inject() 简洁且类型安全，但只能在注入上下文中调用；服务之间也用 inject 组合。
  • InjectionToken 承载配置等非类依赖，optional 加默认值可以优雅降级。
  • 服务内用私有 signal 加只读视图封装状态，computed 负责派生，写入必须走方法。
