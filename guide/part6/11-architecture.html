11 · 大型应用架构与设计模式 ​

所属：第六篇 · 精通　配套示例：architecture

学习目标 ​

  • 画出 core、features 与组件之间的依赖方向，并解释为什么依赖必须向内
  • 用接口加 InjectionToken 让领域层不绑定具体数据源
  • 用 Facade 收敛状态与用例，让组件只读 signal、不碰请求细节
  • 在 app.config.ts 这一处装配点替换实现，而不改业务代码
  • 用 Fake 仓储为 Facade 写不依赖网络的测试

1. 组件直接取数的代价 ​

功能少的时候，组件里注入 HttpClient 最省事：

ts
// 反例：展示、校验、请求与状态都压在一个组件里
export class OrdersPage {
  private readonly http = inject(HttpClient);
  protected readonly orders = signal<Order[]>([]);

  load(): void {
    this.http.get<Order[]>('/api/orders')
      .subscribe((orders) => this.orders.set(orders));
  }
}

这段代码在三个方向上变脆：想换缓存或 IndexedDB 要改组件；想给加载失败加提示要改组件；想脱离网络测试要改组件。更糟的是，第二个页面需要订单列表时，只能复制一遍请求逻辑。

分层不是把文件拆得更多，而是让变化被隔离在一层里。示例把订单功能拆成四块：领域模型、仓储接口、Facade 状态层、展示组件。

2. 机制拆解 ​

2.1 领域模型与仓储接口 ​

Order 只有 id、title、amount、createdAt 四个字段，属于业务模型，不是接口返回的原始 DTO。仓储接口描述「需要什么能力」，不描述「怎么取」：

ts
// 文件：src/app/core/order.repository.ts
export interface OrderRepository {
  list(): Observable<Order[]>;
  create(title: string, amount: number): Observable<Order>;
}

core 只依赖 RxJS 的 Observable 与自身模型，不知道 HTTP、缓存或存储的存在。依赖方向必须指向内层：features/orders 可以 import core，core 不能 import features，组件只能看到 Facade。测试时用 Fake 替换 Token，Facade 的加载、错误与合计逻辑就能脱离网络独立验证。

2.2 用 Token 绑定接口 ​

接口在编译后被擦除，运行时需要一个真实的值作为注入键：

ts
// 文件：src/app/core/tokens.ts
export const ORDER_REPOSITORY = new InjectionToken<OrderRepository>('OrderRepository');
ts
// 文件：src/app/app.config.ts
export const appConfig: ApplicationConfig = {
  providers: [
    provideBrowserGlobalErrorListeners(),
    // 切换真实 HTTP 实现时，只需替换这一行
    { provide: ORDER_REPOSITORY, useClass: InMemoryOrderRepository },
  ],
};

InMemoryOrderRepository 只标了 @Injectable()，没有 providedIn: 'root'，因为它必须通过 Token 注册。app.config.ts 是组合根：唯一知道「接口由哪个实现提供」的地方。

2.3 Facade 收敛状态与用例 ​

ts
// 文件：src/app/features/orders/orders.facade.ts
private readonly repository = inject(ORDER_REPOSITORY);
private readonly state = signal<Order[]>([]);
readonly orders = this.state.asReadonly();
readonly total = computed(() =>
  this.state().reduce((sum, order) => sum + order.amount, 0),
);
readonly loading = signal(false);
readonly error = signal('');

私有可写 signal 加公开只读视图，是 Facade 的基本约束：外部可以读 orders()，但不能绕过用例直接 set。load() 负责把 loading、error 与数据三者一起维护，add() 负责校验并追加。

组件因此只做两件事：把用户输入转成 Facade 调用，把 Facade 的 signal 映射到模板。app.config.ts 是唯一允许依赖具体实现的地方，因为它位于最外层。测试时用 TestBed 把 Token 覆盖为同步 Fake，即可断言 orders()、total() 与 error()。

3.1 建议先改这里 ​

  1. 把 list() 中的 delay(300) 改成 delay(3000)。预期：页面先显示「加载中...」，三秒后列表与合计出现；期间点「新增订单」仍可提交，说明 Facade 未把两类请求串行化。

  3. 在 app.config.ts 中新增一个 FakeOrderRepository 并用 useClass 替换，而不改 app.ts。预期：页面数据变化，组件代码零改动，证明装配点唯一。

4. 代码拆解 ​

4.1 仓储的内存实现 ​

ts
// 文件：src/app/core/order.repository.ts
@Injectable()
export class InMemoryOrderRepository implements OrderRepository {
  private readonly orders: Order[] = [
    { id: 'o-1', title: '年度订阅', amount: 699, createdAt: '2026-10-01' },
    { id: 'o-2', title: '团队扩容', amount: 1299, createdAt: '2026-10-08' },
  ];

  list(): Observable<Order[]> {
    return of(this.orders).pipe(delay(300));
  }

  create(title: string, amount: number): Observable<Order> {
    const order: Order = {
      id: 'o-' + (this.orders.length + 1),
      title,
      amount,
      createdAt: new Date().toISOString().slice(0, 10),
    };
    this.orders.push(order);
    return of(order).pipe(delay(200));
  }
}

delay 模拟网络延迟，让加载态可见；of 保证每次订阅都返回同一份内存数组的引用。真实实现会换成 HttpClient，但方法签名不变，Facade 无需感知。

4.2 Facade 的加载与新增 ​

ts
// 文件：src/app/features/orders/orders.facade.ts
load(): void {
  this.loading.set(true);
  this.error.set('');
  this.repository.list().subscribe({
    next: (orders) => {
      this.state.set(orders);
      this.loading.set(false);
    },
    error: () => {
      this.error.set('订单加载失败，请稍后重试');
      this.loading.set(false);
    },
  });
}

add(title: string, amount: number): void {
  if (!title.trim() || amount <= 0) {
    this.error.set('请填写有效的订单名称与金额');
    return;
  }
  this.error.set('');
  this.repository.create(title.trim(), amount).subscribe((order) => {
    this.state.update((orders) => [...orders, order]);
  });
}

加载开始先清错误，失败时同时收尾 loading；新增先做输入校验，再用 update 返回新数组，保证 signal 通知生效。Facade 没有暴露 repository，组件无法绕过校验直接写数据。组件侧只注入 Facade，在构造函数里触发 load()，提交后清空本地输入 signal，因此没有 HttpClient、仓储或校验规则。

5. 常见坑 ​

现象原因处理
组件里直接注入 InMemoryOrderRepository绕过了 Token，实现与展示耦合只注入 Facade，由组合根决定实现
启动时报 NullInjectorErrorToken 未在 app.config.ts 或组件 providers 注册在组合根用 { provide: ORDER_REPOSITORY, useClass: HttpOrderRepository } 绑定
模板能直接改订单数组Facade 暴露了可写 signal私有 state，只公开 asReadonly() 或派生值
测试必须等真实延时直接使用带 delay 的实现用 useValue 注入同步 Fake
core 反向依赖 features领域层引用了页面状态用接口与模型隔离，把编排逻辑留在 features

6. 练习 ​

  1. 增加按金额排序：在 Facade 中提供 sortByAmount 状态与派生列表，不修改仓储。 验收：切换排序后模板顺序变化，repository 接口没有新增方法。
  2. 处理新增失败：给 create 加错误分支，写入 error 并保持列表不变。 验收：模拟失败后出现提示，订单数量不增加，loading 不残留为 true。
  3. 替换为 HTTP 实现：新增 HttpOrderRepository，在 app.config.ts 换绑，组件保持不动。 验收：只需改动组合根与新增实现文件，app.ts 与 Facade 的 diff 为空。
  4. 为 Facade 写测试：用 Fake 仓储验证合计金额与错误文案。 验收：测试不访问网络、不使用真实计时器，断言 total() 与 error()。

7. 自测 ​

1. 为什么仓储要用 InjectionToken，而不是直接注入类？

接口在运行时不存在，Token 提供稳定的注入键；同时它把「需要什么能力」与「由谁实现」分开。组件和 Facade 只依赖 Token，替换实现时只改组合根，测试时也能注入 Fake。

2. Facade 与普通服务有什么区别？

普通服务可以只封装一个能力；Facade 面向一个用例边界，负责组合仓储、维护加载与错误状态、暴露只读派生值。判断标准是：组件是否只需要与一个对象交互就能完成整个页面。

3. 为什么 `InMemoryOrderRepository` 不加 `providedIn: 'root'`？

因为它必须由 Token 绑定，而不是按类本身注入。若加 providedIn: 'root'，会额外产生一个无人使用的类级单例，也容易让调用方误以为可以直接注入具体类，破坏依赖倒置。

本章小结 ​

  • 分层的目标是隔离变化，不是增加文件数量。
  • 领域模型与仓储接口放在 core，依赖只允许从外向内。
  • InjectionToken 为接口提供运行时键，组合根决定绑定哪个实现。
  • Facade 用私有可写 signal 加公开只读视图收敛状态，组件只做绑定。
  • 可替换性要能被验证：换实现不改业务代码，写测试不碰网络。
