12 · 框架源码级原理 ​

所属：第六篇 · 精通　配套示例：internals

学习目标 ​

  • 解释元素注入器与根注入器的查找顺序，并预测 providers 的覆盖结果
  • 说明 OnPush 组件在哪些通知下才会被检查
  • 区分 detectChanges() 与 markForCheck() 的作用范围与时机
  • 在 zoneless 下判断一次更新由谁调度，并解释普通字段为何不刷新
  • 用可重复实验验证对框架行为的假设，而不是依赖旧版 Zone.js 经验

1. 注入器是一棵树 ​

Angular 的依赖注入不是一张全局表，而是一棵与组件树平行的注入器树。根级 provider 在应用启动时创建，组件上的 providers 会为这个组件及其视图创建一个子注入器：

ts
// 文件：src/app/greeting.ts
export const GREETING = new InjectionToken<string>('GREETING');

@Component({
  selector: 'app-greeting',
  // 组件级 providers 会创建子注入器，覆盖祖先提供的同名 Token
  providers: [{ provide: GREETING, useValue: '来自 Greeting 组件的子注入器' }],
  template: '<p>注入结果：{{ greeting }}</p>',
})
export class Greeting {
  protected readonly greeting = inject(GREETING);
}

根级则通过应用配置提供同一个 Token：

ts
// 文件：src/app/app.config.ts
providers: [
  provideBrowserGlobalErrorListeners(),
  { provide: GREETING, useValue: '根级注入器提供的值' },
],

inject(GREETING) 从当前组件的元素注入器开始查找，逐级向上，最后才到环境注入器。因为 Greeting 自己声明了 provider，它在第一站就命中，根级的值被遮蔽。

关键限制是覆盖只作用于这棵子树。同级的其他组件、父组件都继续读根级值；Greeting 内部再嵌套的子组件会继承组件级值。若把 provider 写到父组件上，影响范围就变成整棵父子树。

@Component 还有 viewProviders，它只对组件的视图子节点可见，对通过内容投影进来的子节点不可见。需要隔离投影内容时，这个区别很重要。

2. 机制拆解 ​

2.1 OnPush 只对通知负责 ​

ts
// 文件：src/app/cd-lab.ts
protected plain = 0;
protected readonly reactive = signal(0);

protected bumpPlainLater(): void {
  // 异步回调修改普通字段：OnPush 下不会自动刷新
  setTimeout(() => {
    this.plain++;
  }, 0);
}

普通字段没有任何机制知道它变了。setTimeout 回调执行完毕后，框架不会收到「需要检查」的通知，因此模板里的数字不动。signal 不同：reactive.update(...) 会通知所有读取过它的视图，调度器随后安排一次刷新。

在旧版 Zone.js 应用里，setTimeout 会被 zone 打补丁并在回调后触发全局检查，所以同样的代码「碰巧」能刷新。zoneless 把这个隐式行为移除了，普通字段必须显式通知。

2.2 zoneless 下的刷新路径 ​

一次 signal 写入大致经过这些步骤：

  1. 写入 signal，标记依赖它的消费者为脏。
  2. 调度器安排一次变更检测（异步，不阻塞当前调用栈）。
  3. 从脏视图向上标记祖先，确保检查路径可达。
  4. 刷新过程中检查被标记的视图，更新 DOM。

模板事件绑定是另一条入口：点击按钮时，框架会把该组件视图标记为脏并安排刷新。两条路径最终都汇合到同一套调度，而不是每次事件后全量扫描整棵树。

2.3 detectChanges 与 markForCheck ​

ts
protected refresh(): void {
  // 手动通知本组件检查并刷新视图
  this.cdr.detectChanges();
}

detectChanges() 是同步的，立即检查当前视图及其子视图，不管 OnPush 标记；它不会刷新祖先，也不会安排后续 tick。适合「我知道数据刚变、必须马上同步 DOM」的场景，例如测量元素尺寸前。

markForCheck() 不执行检查，只把当前视图到根的路径标记为需要检查，然后等待下一次调度。它不保证立刻更新，但能与框架的批处理配合，是 OnPush 组件在异步回调里的常规选择。

手段作用范围时机
signal 写入依赖该 signal 的视图异步调度
模板事件绑定当前组件视图异步调度
markForCheck()当前视图到根路径下一次 tick
detectChanges()当前视图及子视图同步立即

4. 代码拆解 ​

4.1 组件级 provider 的覆盖 ​

ts
// 文件：src/app/greeting.ts
@Component({
  selector: 'app-greeting',
  // 组件级 providers 会创建子注入器，覆盖祖先提供的同名 Token
  providers: [{ provide: GREETING, useValue: '来自 Greeting 组件的子注入器' }],
  template: '<p>注入结果：{{ greeting }}</p>',
  styles: ':host { display: block; padding: 12px; background: #f9fafb; border-radius: 8px; }',
})
export class Greeting {
  protected readonly greeting = inject(GREETING);
}

4.2 OnPush 实验组件 ​

ts
// 文件：src/app/cd-lab.ts
@Component({
  selector: 'app-cd-lab',
  changeDetection: ChangeDetectionStrategy.OnPush,
  templateUrl: './cd-lab.html',
  styleUrl: './cd-lab.css',
})
export class CdLab {
  private readonly cdr = inject(ChangeDetectorRef);

  protected plain = 0;
  protected readonly reactive = signal(0);

  protected bumpPlainLater(): void {
    setTimeout(() => {
      this.plain++;
    }, 0);
  }

  protected refresh(): void {
    this.cdr.detectChanges();
  }

  protected bumpReactive(): void {
    this.reactive.update((value) => value + 1);
  }
}

三个按钮对应三条路径：无通知的异步写入、显式同步检查、signal 自动调度。模板同时绑定 plain 与 reactive()，因此能直接看出哪条路径刷新了哪一个值。

4.3 根组件只负责组合 ​

ts
// 文件：src/app/app.ts
@Component({
  selector: 'app-root',
  imports: [Greeting, CdLab],
  templateUrl: './app.html',
  styleUrl: './app.css',
})
export class App {}

standalone 组件通过 imports 引入依赖的组件。根组件不参与实验逻辑，两个子组件各自拥有独立的注入器与变更检测状态。

6. 练习 ​

  1. 验证继承边界：在 Greeting 模板里再放一个子组件，让它也注入 GREETING。 验收：子组件读到组件级值；把该子组件移到 Greeting 外部后，改读根级值。
  2. 替换刷新方式：把「手动 detectChanges」按钮改为调用 markForCheck()，并在控制台记录调用顺序。 验收：页面仍会更新，但发生在下一轮调度，而不是点击调用栈内。
  3. 混合通知：在 bumpPlainLater 的回调里先递增 plain，再 reactive.update。 验收：一次操作后两个数字同时变化，说明 signal 通知会带上同一视图里的普通字段。

7. 自测 ​

1. 组件级 providers 会覆盖根级，为什么兄弟组件不受影响？

provider 注册在组件自己的元素注入器上，查找从当前节点向上进行。兄弟组件不在 Greeting 的子树里，查找路径不经过它的注入器，因此仍命中根级值。覆盖的范围是子树，不是全局。

2. detectChanges 与 markForCheck 的本质区别是什么？

detectChanges() 同步执行检查，范围是当前视图及子视图，绕开 OnPush 的脏标记；markForCheck() 只打标记并让检查路径可达，实际检查由后续调度完成。前者适合必须立即同步 DOM 的场景，后者适合同步之外的异步回调。

3. 为什么 zoneless 下改普通字段不会刷新？

zoneless 不依赖 Zone.js 拦截异步任务，只响应明确的通知：signal 写入、模板事件、markForCheck()、AsyncPipe 等。setTimeout 修改普通字段没有产生任何通知，调度器不知道需要检查，视图自然保持不变。

本章小结 ​

  • 注入器树与组件树平行，组件 providers 创建子注入器，覆盖只影响子树。
  • inject() 依赖注入上下文，字段初始化是安全位置，事件回调不是。
  • OnPush 不是「不检查」，而是「只对通知响应」；zoneless 让通知来源变得显式。
  • detectChanges() 同步且局部，markForCheck() 异步且向上，选择取决于时机要求。
  • 框架行为可以用最小实验验证：改一个 provider、换一种通知方式，观察差异。
