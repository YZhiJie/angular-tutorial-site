08 · 测试与质量门禁 ​

所属：第四篇 · 工程化　配套示例：testing-lab

学习目标 ​

  • 能把计价逻辑从组件中提取为可独立测试的纯函数
  • 能用 Vitest 的 describe / it / expect 覆盖正常路径与边界条件
  • 能说明 ng test 在 Angular 22 中实际调用的构建器与测试运行器
  • 能判断什么时候需要 TestBed，什么时候它只会增加成本
  • 能用 TestBed.createComponent 验证「signal → computed → 模板」链路
  • 能用 HttpTestingController 替身 HTTP 请求，断言请求方法与响应处理

1. 先让逻辑可测，再谈怎么测 ​

示例把金额计算全部放进 price.ts，组件只负责展示。subtotal 累加「单价 × 数量」， applyDiscount 处理折扣与两位小数舍入，并对非法折扣率抛出 RangeError。

ts
// 文件：src/app/price.ts
export function subtotal(items: CartItem[]): number {
  return items.reduce((sum, item) => sum + item.price * item.quantity, 0);
}

export function applyDiscount(amount: number, rate: number): number {
  if (rate < 0 || rate > 1) {
    throw new RangeError('折扣率必须在 0 到 1 之间');
  }
  return Math.round(amount * (1 - rate) * 100) / 100;
}

这两个函数没有依赖注入、没有 DOM、没有 signal，输入确定则输出确定。测试它们不需要 Angular 运行时，也不需要异步等待，一条断言就是一个业务规则。组件则用 computed 把纯函数接到 signal 上：

ts
// 文件：src/app/app.ts
protected readonly subtotal = computed(() => subtotal(this.items()));
protected readonly discounted = computed(() => applyDiscount(this.subtotal(), 0.1));

如果一开始就把累加逻辑写进组件方法，测试就必须创建组件、准备渲染环境、读取 DOM 文本才能验证一个加法；逻辑越靠近纯函数，测试越接近「直接调用、直接断言」。

2. 测试分层与 Vitest 的实际行为 ​

纯函数测试：基线。 示例的 src/app/price.spec.ts 从 vitest 显式导入 describe、expect、 it，按函数分组，覆盖多商品、空购物车、折扣舍入与非法参数。

ts
// 文件：src/app/price.spec.ts
import { describe, expect, it } from 'vitest';
describe('subtotal', () => {
  it('空购物车返回 0', () => {
    expect(subtotal([])).toBe(0);
  });
});

describe('applyDiscount', () => {
  it('非法折扣率抛出 RangeError', () => {
    expect(() => applyDiscount(100, 1.2)).toThrow(RangeError);
  });
});

ng test 跑的是什么。 示例的 angular.json 把 test 目标指向 @angular/build:unit-test， 依赖里安装了 vitest 5 与 jsdom。执行 ng test 时，构建器编译 TypeScript（包含 Angular 模板 类型检查）、收集 *.spec.ts，再交给 Vitest 在 jsdom 环境里运行；tsconfig.spec.json 的 include 覆盖 src/**/*.spec.ts（以及 src/**/*.d.ts）。测试仍然是 zoneless 的，不需要浏览器 窗口；zone.js 只作为构建器的可选解析目标存在于 devDependencies，应用启动路径不加载它。

bash
ng test --watch=false  # CI 中只跑一次，失败时以非零状态退出

示例现在有三个测试文件，分别覆盖三层：

文件层级验证对象
price.spec.ts纯函数累加、折扣舍入、非法参数
app.spec.ts组件（TestBed）signal → computed → 模板的渲染结果
user.service.spec.ts服务（HTTP 替身）请求方法、响应裁剪、错误分支

TestBed 的适用边界。 只有当测试对象涉及依赖注入、模板渲染、DOM 事件、路由或表单交互时， TestBed 才值得出场。app.spec.ts 先用 configureTestingModule 导入 standalone 组件，再创建 fixture 并触发首次变更检测：

ts
// 文件：src/app/app.spec.ts
beforeEach(async () => {
  await TestBed.configureTestingModule({
    imports: [App],
    providers: [provideHttpClient()],
  }).compileComponents();
});

it('渲染纯函数计算的小计与折后价', () => {
  const fixture = TestBed.createComponent(App);
  fixture.detectChanges();
  const text = fixture.nativeElement.textContent as string;
  expect(text).toContain('1256');
  expect(text).toContain('1130.4');
});

组件测试更慢、更脆弱，但能验证「signal → computed → 模板」这条链路确实接通。App 注入了 UserService，所以即使测试不点击加载按钮，也必须提供 HttpClient，否则创建组件时就会注入失败。

HttpTestingController：把网络变成可断言的对象。 服务测试不应该请求真实接口。示例用 provideHttpClientTesting() 替换后端，expectOne 捕获请求，flush 返回构造数据，verify 确认没有遗留请求：

ts
// 文件：src/app/user.service.spec.ts
const req = http.expectOne(URL);
expect(req.request.method).toBe('GET');
req.flush([
  { id: 1, name: 'A', email: 'a@example.com' },
  // ...
]);
expect(result?.length).toBe(3);

req.error(new ProgressEvent('error')) 可以模拟网络失败，用来验证错误分支。真实接口的响应结构、 超时与重试策略都可以在这一层确定，测试运行不依赖网络。

质量门禁。 测试通过只是其中一环。一条可执行的门禁通常按顺序运行：先 pnpm check:examples 校验示例元数据、生成物与沙箱哈希，再 pnpm build:examples 确认生产构建与预算，然后 pnpm test:examples 跑 Vitest，最后 pnpm docs:build 确认站点可构建。预算让「包变大」变成构建 失败，测试让「行为变了」变成红灯，两者共同阻止回退。

可测试的计价模块

纯函数优先的测试设计，配合 Vitest 运行单元测试。

示例会在滚动到此处时加载，首次启动需要等待依赖安装。

3.1 建议先改这里 ​

  1. 把 app.ts 初始数据中「机械键盘」的数量从 2 改成 3。验收：页面小计从 1256 变为 1655， 折后价变为 1489.5，界面无需手动刷新。
  2. 把 applyDiscount 的返回值改成 Math.round(amount * (1 - rate))，然后运行 npm test （等价于 ng test）。验收：applyDiscount 的舍入用例失败，Vitest 输出期望值与实际值。
  3. 在 price.spec.ts 中新增折扣率为 0 和 1 的断言。验收：折扣率 0 返回原金额，折扣率 1 返回 0。
  4. 把非法折扣率的测试改成 expect(() => applyDiscount(100, -0.1)).toThrow(RangeError)。验收： 测试通过，说明负数同样被拦截。
  5. 在仓库根目录运行 pnpm test:examples。验收：终端输出 3 个测试文件、7 条用例全部通过，且没有 发起真实网络请求。

4. 代码拆解 ​

纯函数模块先定义数据结构，再实现两个函数。applyDiscount 把校验放在计算之前，非法输入不会 产生「看起来合理」的数字；舍入使用「乘 100、取整、再除 100」，保证金额保留两位小数。

ts
// 文件：src/app/price.ts
export interface CartItem {
  name: string;
  price: number;
  quantity: number;
}

export function subtotal(items: CartItem[]): number {
  return items.reduce((sum, item) => sum + item.price * item.quantity, 0);
}

测试文件按被测函数分组。多商品用例验证累加，空数组用例验证单位元，折扣用例同时覆盖正常舍入 与异常分支。toThrow(RangeError) 断言的是错误类型，而不是错误文案，因此修改提示语不会误伤测试。

ts
// 文件：src/app/price.spec.ts
it('累加多个商品', () => {
  const items: CartItem[] = [
    { name: '键盘', price: 399, quantity: 2 },
    { name: '鼠标', price: 199, quantity: 1 },
  ];
  expect(subtotal(items)).toBe(997);
});

it('按折扣率计算并保留两位小数', () => {
  expect(applyDiscount(100, 0.15)).toBe(85);
  expect(applyDiscount(99.99, 0.1)).toBe(89.99);
});

服务层把 HTTP 细节单独收拢。UserService.list() 只负责请求、超时与前三位裁剪；测试用 HttpTestingController 接管这条链路，不需要启动服务器。

ts
// 文件：src/app/user.service.ts
list(): Observable<User[]> {
  return this.http.get<User[]>(URL).pipe(
    timeout(8000),
    map((users) => users.slice(0, 3)),
  );
}
ts
// 文件：src/app/user.service.spec.ts
beforeEach(() => {
  TestBed.configureTestingModule({
    providers: [UserService, provideHttpClient(), provideHttpClientTesting()],
  });
  service = TestBed.inject(UserService);
  http = TestBed.inject(HttpTestingController);
});

afterEach(() => http.verify());

组件把 signal 与纯函数连接起来。items 是唯一数据源，两个 computed 只做组合，不包含分支逻辑， 因此组件层不需要重复测试同一套算法。

ts
// 文件：src/app/app.ts
protected readonly items = signal<CartItem[]>([
  { name: '机械键盘', price: 399, quantity: 2 },
  { name: '人体工学鼠标', price: 199, quantity: 1 },
  { name: '显示器支架', price: 259, quantity: 1 },
]);

protected readonly subtotal = computed(() => subtotal(this.items()));
protected readonly discounted = computed(() => applyDiscount(this.subtotal(), 0.1));

模板只负责展示，列表用 track item.name，金额直接读取 computed，把「页面正确」与「逻辑正确」区分成两个验证动作。

html
<!-- 文件：src/app/app.html -->
@for (item of items(); track item.name) {
  <li><span>{{ item.name }}</span><span class="muted">{{ item.price }} × {{ item.quantity }}</span></li>
}
<dt>小计</dt><dd>{{ subtotal() }} 元</dd>
<dt>九折后</dt><dd class="hot">{{ discounted() }} 元</dd>

5. 常见坑 ​

现象原因处理
一个加法也要创建组件才能测逻辑写在组件方法里提取纯函数，组件只做组合
测试全绿但线上出错只覆盖正常路径补空数组、0、1、非法参数等边界
浮点断言偶发失败二进制浮点无法精确表示小数金额先舍入到两位，或使用 toBeCloseTo
纯函数测试也套 TestBed没有 DI、模板或 DOM 需求直接调用函数，减少启动成本
CI 中 ng test 一直不退出监听模式没有关闭使用 ng test --watch=false
新增的 spec 没被执行文件名不符合 *.spec.ts按约定命名并确认 tsconfig.spec.json 的 include
组件测试读取文本却拿不到值创建后没有触发首次变更检测调用 fixture.detectChanges()
创建组件时注入失败组件依赖的服务没有在 TestBed 中提供补 providers，例如 provideHttpClient()
HTTP 测试结束时报未消费请求只断言结果，没有 expectOne / verify先 expectOne，再 flush 或 error，最后 verify()
测试真的访问了外网用了真实 HttpClient 后端加上 provideHttpClientTesting() 替身

6. 练习 ​

  1. 为 subtotal 增加「数量为 0」与「空数组」两个用例。验收：两者都返回 0，且测试不依赖 DOM。
  2. 为 applyDiscount 增加边界用例：折扣率 0 返回原金额，折扣率 1 返回 0，折扣率 -0.1 抛出 RangeError。验收：三个用例全部通过。
  3. 新增纯函数 bulkDiscount(items)：商品件数达到 3 件时减免 50 元，否则返回原小计。验收： 为 2 件、3 件、空数组各写一条断言，并全部通过。
  4. 在已有的 app.spec.ts 里追加一条断言：页面包含「远程用户」文案。验收：ng test --watch=false 通过；你能说明这条测试比纯函数测试多验证了什么。
  5. 在 user.service.spec.ts 中新增一条用例：req.flush([]) 后结果为长度为 0 的数组，且 repository 不抛错。验收：http.verify() 通过，说明空响应也被正确裁剪。
  6. 给 UserService.list() 增加一次重试（retry(1)），再写一条「第一次错误、第二次成功」的测试。 验收：http.expectOne 被调用两次，最终结果为成功数据。

7. 自测 ​

1. 为什么示例把计价逻辑放在纯函数里，而不是组件方法里？

纯函数没有 DI、DOM 与生命周期依赖，测试只需构造输入、断言输出，运行快且稳定。组件方法要经过 TestBed、模板渲染与变更检测才能验证同一个加法，成本高且失败原因不直观。

2. 什么情况下应该使用 TestBed？

需要验证依赖注入、模板绑定、DOM 事件、路由或表单交互时。若测试对象只是一个不依赖 Angular 运行时的计算函数，TestBed 不提供额外价值，只会拖慢测试并引入环境变量。

3. `ng test` 在示例项目里实际做了什么？

它调用 angular.json 中配置的 @angular/build:unit-test 构建器，编译 TypeScript 与模板， 收集 src/**/*.spec.ts，再交给 Vitest 在 jsdom 环境运行。CI 中用 --watch=false 只跑一次， 失败时以非零退出码结束。

本章小结 ​

  • 先把业务规则提取成纯函数，测试才能快速、稳定、直接地断言。
  • Vitest 负责断言与用例组织，ng test 通过 Angular 构建器完成编译与收集。
  • TestBed 只用于 DI、模板与 DOM 交互，不应成为所有测试的默认起点。
  • HTTP 测试用 HttpTestingController 替身后端，断言请求方法、响应裁剪与错误分支。
  • 边界与异常分支比「再多一个正常用例」更能暴露真实缺陷。
  • 测试加构建预算构成质量门禁；上一章：07 懒加载与构建优化， 下一章：09 大列表性能调优。
